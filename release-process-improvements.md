# Прозрачный релизный процесс: артефакты для Confluence

Документ содержит:
1. Шаблон таблицы статуса релизов (CSV + HTML) — для импорта в Confluence.
2. Описание полей таблицы и регламент её обновления.
3. Предложения по улучшению релизного процесса.
4. Предложения по НФТ (нефункциональному тестированию).

---

## 1. Файлы для Confluence

| Файл | Назначение | Как импортировать |
| --- | --- | --- |
| `release-status-table.csv` | Исходник таблицы, легко редактируется и версионируется в git | Confluence Cloud: `/table` → «Paste from spreadsheet». Для DC/Server — макрос **Table from CSV** из аддона *Table Filter and Charts* |
| `release-status-table.html` | Готовая свёрстанная таблица со стилями и цветами статусов | Открыть в браузере → Ctrl+A / Ctrl+C → вставить в страницу Confluence. Либо через редактор «View storage format» вставить `<table>` целиком |

Рекомендуется разместить страницу в пространстве `QA` → `Releases` → `Release Dashboard` и закрепить в сайдбаре пространства, чтобы менеджмент и стейкхолдеры открывали её в один клик.

## 2. Поля таблицы и регламент обновления

### Блоки колонок

- **Идентификация релиза**: `Release`, `Версия`, `Релиз-менеджер`, `QA Lead`.
- **Таймлайн**: `Code freeze`, `Плановая дата релиза`, `Фактическая дата релиза`.
- **Состояние**: `Окружение` (dev / stage / prod), `Статус` (Planning → In Dev → In QA → UAT → RC → Released / Rolled back).
- **Скоуп**: ключевые фичи, ссылка на Jira-фильтр (`fixVersion = R-YYYY.MM`), счётчики задач.
- **Качество**: дефекты по severity (Blocker / Critical / Major / Minor), reopen, % автопокрытия.
- **Тесты**: smoke, regression, НФТ (нагрузочное, стресс, security, отказоустойчивость).
- **Операционная готовность**: feature flags, миграции БД, rollback-план, мониторинг, SLO.
- **Риски и решения**: риски, Go/No-Go, sign-off QA / PO / SRE.
- **Артефакты**: Test Plan, Test Report, Runbook, дашборды.

### Правила обновления

| Фаза | Частота | Ответственный |
| --- | --- | --- |
| Planning | при изменении скоупа | Релиз-менеджер + QA Lead |
| In Dev | раз в день | QA Lead (цифры из Jira/Zephyr) |
| In QA / UAT | 2 раза в день (утро/вечер) | QA Lead |
| Pre-release (за 24ч) | в реальном времени | QA Lead + SRE |
| Post-release | в течение 2 часов после выката | Релиз-менеджер |

Все изменения должны быть отражены в колонке `Комментарий` коротким пунктом с датой.

## 3. Предложения по улучшению релизного процесса

### 3.1. Единый источник истины и автоматизация

- **Автоматически наполнять таблицу из Jira/TestRail** через Confluence-макрос *Jira Issues* и сохранённые JQL-фильтры по `fixVersion`. Счётчики (всего / готово / в тесте / done / reopen / по severity) перестанут быть «ручной бухгалтерией».
- **Release notes в один клик**: шаблон страницы с макросом Jira, фильтр `fixVersion = Rx AND status = Done`, ссылка на этот шаблон — в колонке «Ссылки».
- **Dashboard в Grafana/Datadog** с метриками релиза (errors rate, p95 latency, saturation) — ссылка на дашборд живёт в таблице в колонке `Monitoring`.
- **Boт-нотификации в Slack/Teams** по смене статуса релиза: при переходе `In QA → RC → Released / Rolled back` бот постит дифф по таблице. Менеджмент получает апдейт автоматически, без созвонов.

### 3.2. Предсказуемость и «контракты» фаз

- **Definition of Ready to QA (DoR)**: задача переходит в QA только при выполнении чеклиста — юнит-тесты зелёные, деплой на stage, чеклист безопасности, обновлённый Test Design. Это режет reopen и простои QA.
- **Definition of Done (DoD)** релиза: smoke + regression pass, все Blocker/Critical закрыты, НФТ-отчёт опубликован, runbook обновлён, sign-off от QA/PO/SRE. Без галочек релиз не катим.
- **Release train** с фиксированной каденцией (например, каждый четверг). Фичи, не успевшие к code freeze, автоматически переезжают на следующий поезд — это убирает «закидывание» в последний день.
- **Go/No-Go-митинг 30 минут** с явными критериями (а не «поговорить»). Таблица — главный артефакт митинга.

### 3.3. Quality gates в CI/CD

- Pre-merge: lint + unit + contract tests (должны проходить за ≤ 10 минут).
- Post-merge на `main`: integration + e2e smoke на эфемерном окружении.
- На staging: полный regression (параллелизация Playwright/Cypress, селективный прогон по импакт-анализу).
- На проде: canary (1% → 5% → 25% → 100%) с автоматическим rollback по SLO.

### 3.4. Управление дефектами

- Единый SLA реакции: Blocker — 2ч, Critical — 8ч, Major — 48ч, Minor — до следующего релиза.
- Обязательный **bug bash** за 1 день до code freeze (вся команда, 1.5 часа).
- Постмортем на любой Blocker, утёкший на прод — коротко, без blame, с action items в ту же таблицу.

### 3.5. Прозрачность без созвонов

- Еженедельный авто-дайджест (e-mail / Slack) с выжимкой из таблицы: что вышло, что в RC, какие риски, Go/No-Go по следующему релизу.
- Публичный календарь релизов в Confluence (макрос *Team Calendars* или просто страница с таблицей).
- «Status page» для стейкхолдеров: только колонки Release / Версия / Статус / Риски / Go-No-Go — остальное скрыто фильтром.

## 4. Предложения по НФТ (non-functional testing)

Цель — закрыть риски, которые функциональные тесты не видят, и сделать результаты НФТ частью Go/No-Go.

### 4.1. Нагрузочное и стресс-тестирование

- Инструменты: **k6** (скриптуется в JS, отлично ложится в CI), **Locust** или **Gatling** для сложных сценариев.
- Сценарии и целевые SLO:
  - *Baseline* — ожидаемая нагрузка (например, 300 RPS), цель: p95 ≤ 300 мс, error rate < 0.1%.
  - *Peak* — 3× baseline в течение 30 минут.
  - *Soak* — 60–70% baseline в течение 4–8 часов (ищем утечки памяти/дескрипторов).
  - *Stress* — наращиваем нагрузку до отказа, фиксируем точку деградации.
  - *Spike* — мгновенный ×5, проверяем автоскейлинг.
- Прогон на каждом major-релизе и при изменении инфраструктуры/критичных сервисов. Для минорных — smoke-load (5 минут, baseline).
- Отчёт k6 публикуется в Confluence страницу релиза + прикрепляется ссылка в главную таблицу.

### 4.2. Отказоустойчивость / Chaos

- Регулярные chaos-эксперименты: убиваем pod, симулируем потерю зоны, деградацию БД, сетевые задержки. Инструменты: **Chaos Mesh**, **Litmus**, **Gremlin**.
- Game days раз в квартал: отрабатываем runbook на staging.
- Метрики успеха: время обнаружения (MTTD) и восстановления (MTTR) по SLO.

### 4.3. Безопасность (shift-left)

- **SAST**: SonarQube / Semgrep на каждый PR.
- **SCA**: Trivy / Snyk / Dependabot — алерты по CVE зависимостей.
- **DAST**: OWASP ZAP на staging перед релизом.
- **Secret scanning**: gitleaks в pre-commit hook и CI.
- **IaC scanning**: tfsec / checkov для Terraform.
- Квартальный pentest критичных модулей (внешний/внутренний).
- Правило: High/Critical CVE и OWASP Top-10 High — блокируют релиз.

### 4.4. Производительность UI

- Lighthouse CI на ключевые страницы; бюджеты: LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1.
- RUM (Real User Monitoring) на проде (Sentry / Datadog RUM) — сравнение до/после релиза.

### 4.5. Доступность (a11y)

- axe-core / Pa11y в e2e-тестах; целевой уровень WCAG 2.1 AA для публичных страниц.

### 4.6. Совместимость и локализация

- Матрица поддерживаемых браузеров/устройств (BrowserStack/Sauce) — прогоняется на RC.
- Проверка локализаций: отсутствующие ключи, длина строк, форматы дат/чисел.

### 4.7. Наблюдаемость как часть DoD

- Каждый релиз обязан поставить: логи (структурированные), метрики (RED/USE), трейсинг (OpenTelemetry), алерты на критичные SLO.
- Если метрики/алертов нет — фича не считается «Done» и не идёт в релиз.

---

## 5. Что это даёт менеджменту

- Одна ссылка в Confluence = полный статус релизов на сегодня.
- Нет «давайте созвонимся» — статусы, риски и Go/No-Go видны, обновляются по расписанию, ключевые события прилетают в Slack.
- Регламент sign-off снимает вопрос «кто отвечает» — в таблице фиксируются QA, PO, SRE с датой.
- НФТ становится не разовой активностью, а встроенной частью релиза с чёткими критериями блокировки.
