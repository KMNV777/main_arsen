Обзор

Процесс выпуска релиза ЕАРМ построен по «Эталонному процессу выпуска релиза» (Confluence NEDRA, этапы 0–12) и «Менеджменту команд разработки» (Jira). Нумерация шагов повторяет этапы эталона; новое отмечено ★. Всего 36 шагов, 3 контура (НЕДРА, ИБ ГПН-ЦР, ГПН-ЦР) и git-дорожка.

Цели
  1. Прозрачно показать параллельные и последовательные действия цикла.
  2. Каждый шаг — задача Jira → время работы и ожидания по этапам.
  3. Чётко разделить зоны ответственности.
  4. Видеть, где, кем и на каком шаге допущены ошибки, где ошибаемся в оценке, где нарушаются требования.
  5. Сервис — часть процесса: в заголовке каждой схемы, в задачах и в матрице «сервис × этап».
Решения владельца процесса
  • Ветка режется от master.
  • ПТЗ — при необходимости; флаг «Требуется ПТЗ» ставит релиз-инженер НЕДРА (шаг 6.1 опциональный).
  • Hotfix идёт тем же процессом (все этапы и ИБ-gates).
  • Юрченко Д. — релиз-инженер НЕДРА.
  • БД — администратор БД Ибрагимов; брокеры — Степуляк.
  • Список сервисов пока не трогаем (плейсхолдеры).
  • SLA шагов — от 1 до 5 рабочих дней; для каждого шага ИБ — 5 дней.
  • Уязвимости, аудит и релиз-борд — зона ответственности релиз-инженера НЕДРА.

Схемы (встроены, масштабируются)

Последовательность и параллельность

  1. Ф0–Ф1 (последовательно): 0.1 → 0.3 → 0.2 → 1.1 → 1.2 (Scope freeze) → 1.3 (freeze ветки, rc на UAT). ПМТ (3.1) стартует сразу, если ПСИ = Да.
  2. Ф2 — параллельный блок P после rc: A = 4.1 → 4.2 → 4.3 ⇄ 4.4 (+ 4.5), B = 2.1 → 2.2 (gate ИБ), C = 3.1 → 3.2 → 3.3 (опц.). Стык — G1 «Код-фриз» (AND-join), фиксируется hash.
  3. Ф3 — цепочка ИБ-gates: 5.1 → 5.2 (аудит) → 6.1 (ПТЗ, если нужен) → 7.2 → 8.1 (трансфер). TOML (7.1) готовится параллельно аудиту и стыкуется на 7.2.
  4. Ф4: 9.1 ‖ 9.2 (БД) ‖ 9.3 (брокеры) → 10.1 → 10.2 → G2 Go/No-Go (No-Go → hotfix-цикл по полному процессу).
  5. Ф5: 11.1 → 12.1 → 12.2 (БД) ‖ 12.3 (брокеры) → 12.4 (post-check) → 12.5 (merge в master) → 12.6 (закрытие, ретро).

SLA и критический путь

Норматив шага — от 1 до 5 рабочих дней; приём PR (1.1) идёт весь спринт и в SLA не входит. Расчёт — самая длинная цепочка от rc (1.3) до закрытия (12.6).

только ПСИ377.41.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6
только ПТЗ428.41.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 6.1 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6
без ПСИ и ПТЗ377.41.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6

Вывод (F17): если каждый шаг использует свой потолок, путь занимает 37–42 рабочих дней (≈ 7–8.4 нед.), а календарь эталона закладывает ≈ 15 рабочих дней. Цепочка аудит → ПТЗ → трансфер по SLA — 12–17 рабочих дней (из них шаги самой ИБ — 10–15) против ≈ 5 рабочих (7 календарных) в календаре. SLA — потолок, не норма: нужны целевые значения и пересборка календаря по критическому пути.

master = состояние Прода; release/<сервис>/<версия> режется от master в начале спринта; hotfix — от ветки Прода.

Включаем, если выполнены ВСЕ условия
  • Story/Bug с fixVersion (Task QA/BE/FE в состав не входят)
  • есть оценка
  • привязаны тест-кейсы (или исключение RO + QA)
  • есть кодовый инкремент: PR → ключ Story
  • приложены скрипты миграции
  • уязвимости по сервису закрыты по ходу спринта
  • при ПСИ — ПМТ покрывает изменение
Не включаем, если
  • нет тест-кейсов без согласованного исключения
  • нет оценки или кодового инкремента
  • нет скриптов миграции там, где они нужны
  • зависит от задачи вне Fix Version
  • приём после Scope freeze без change control
  • нужен ПСИ, но нет ПМТ

Риск F1 — пересечение циклов. Релиз выходит раз в ~4 недели, цикл длиннее: ветка следующего релиза режется, пока предыдущий ещё не в Проде. Правило: ветка N+1 режется от master; после 12.5 релиза N его изменения вливаются в release N+1 и в master.

Jira и Confluence

  • Релизный Epic (квартал) — как в эталоне; Fix Version — состав релиза (Story/Bug); паспорт REL-XXX и календарь в Confluence — витрина.
  • Задача шага (Enabler/Task в Релизном Epic с fixVersion) на каждый шаг реестра: ID шага, роль/ЗО, оценка, исполнитель, результат (✓/↩/✗), код ошибки, этап внесения, «Возврат из».
  • Под-задача сервиса для шагов по сервису (0.2, 1.1, 1.3, 2.1, 4.3, 9.1, 12.x) с обязательным полем «Сервис».
  • Workflow: Ожидает → В работе → Готово; старт/финиш — источник метрик. Возврат = новая задача того же шага + ссылка «Возврат из» + код E + этап внесения.
  • Не источник метрик: календарь и паспорт (обновляются вручную). Факт времени до внедрения списания (I кв. 2027) — переходы статусов.
