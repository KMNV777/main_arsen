# Процесс ведения релизного тикета в Jira

## 1. Цель

Обеспечить единообразное ведение релизов и **автоматизируемую сборку changelog для специалистов информационной безопасности (ИБ)**. К релизному тикету прикрепляются **только истории (Story)**. Задачи и баги связываются со Story — не с релизом напрямую.

---

## 2. Типы тикетов и иерархия связей

| Тип тикета | Кто создаёт | К кому линкуется | Назначение |
|------------|-------------|------------------|------------|
| **Релизный тикет** (Release / Релиз) | РП | — (корневой) | Контейнер релиза, версия, дата, статус |
| **Story** (История) | РП | **Релизный тикет** (`is child of` / `Fix Version`) | Единица changelog для ИБ |
| **Task** (Задача) | РП | **Story** (`is child of`) | Декомпозиция разработки |
| **Bug** (Баг) | Тестировщик | **Story** (`is caused by` / `relates to`) | Дефект, найденный при тестировании Story |

### Правило «только Story в релизе»

```
Релизный тикет
  └── Story (1..N)          ← единственный прямой линк к релизу
        ├── Task (0..N)     ← линк только к Story
        └── Bug (0..N)      ← линк только к Story
```

**Запрещено:** линковать Task или Bug напрямую к релизному тикету.

---

## 3. Роли и зоны ответственности

| Роль | Ответственность |
|------|-----------------|
| **РП** (руководитель проекта / релиз-менеджер) | Создание релизного тикета; заведение Story; заведение Task; контроль полноты релиза; финальная сборка changelog |
| **Аналитик** | Описание Story: бизнес-цель, критерии приёмки, влияние на ИБ, затрагиваемые компоненты/данные |
| **Тестировщик** | Заведение Bug при обнаружении дефекта; линк Bug → Story; верификация исправлений |
| **Разработчик** | Работа в Task; закрытие Task; исправление Bug, привязанных к Story |

---

## 4. Жизненный цикл релиза (пошагово)

### Этап 0. Подготовка релиза

1. РП создаёт **релизный тикет**:
   - ключ версии (например, `v2.4.0`);
   - плановая дата;
   - окружение (staging / production);
   - чек-лист готовности (все Story в статусе «Готово к релизу»).

### Этап 1. Заведение Story

2. РП создаёт **Story** и линкует её к релизному тикету.
3. Аналитик заполняет описание Story (обязательные поля — см. §5).
4. Story переводится в статус **«Готова к разработке»** после ревью аналитиком/РП.

### Этап 2. Декомпозиция на Task

5. РП (или по согласованию — тимлид) создаёт **Task** и линкует каждую к родительской Story.
6. Разработчики берут Task в работу. Статусы Task не влияют на видимость в релизе — в релизе видна только Story.

### Этап 3. Тестирование и баги

7. Тестировщик тестирует функциональность Story.
8. При обнаружении дефекта тестировщик создаёт **Bug** и линкует его к **Story**, в рамках которой найден дефект (не к релизу и не к Task, если только Task не используется как уточнение в комментарии).
9. После исправления Bug закрывается; Story остаётся в релизе.

### Этап 4. Готовность к релизу

10. Все Task по Story закрыты.
11. Все критичные/блокирующие Bug по Story закрыты.
12. РП переводит Story в статус **«Готово к релизу»** / **Done**.
13. Релизный тикет переходит в **«Готов к выкладке»**.

### Этап 5. Сборка changelog для ИБ

14. РП (или автоматизация Jira) выбирает все Story, прилинкованные к релизному тикету.
15. Из полей Story формируется changelog:
    - название;
    - описание (от аналитика);
    - блок «Влияние на ИБ»;
    - затрагиваемые системы/данные;
    - риски.
16. Changelog передаётся специалистам ИБ **до** выкладки в production.

### Этап 6. Выкладка и закрытие

17. После согласования ИБ — деплой.
18. Релизный тикет → **«Выкатан»** → **«Закрыт»**.

---

## 5. Обязательные поля Story (для changelog ИБ)

Аналитик заполняет при создании/уточнении Story:

| Поле | Описание |
|------|----------|
| **Название** | Кратко, понятно для ИБ (что изменилось) |
| **Описание / бизнес-цель** | Зачем делаем, для кого |
| **Критерии приёмки** | Как проверить готовность |
| **Влияние на ИБ** | Новые интеграции, доступы, ПДн, криптография, аудит |
| **Затрагиваемые компоненты** | Сервисы, БД, API, внешние системы |
| **Уровень риска** | Низкий / Средний / Высокий |
| **Fix Version** | Версия релиза (дублирует линк к релизному тикету) |

## 6. Правила линковки в Jira

### 6.1. Матрица допустимых связей

| Связь | Тип линка Jira | Направление | Кто создаёт | Обязательность |
|-------|----------------|-------------|-------------|----------------|
| Story → Релиз | `is child of` / Epic Link / Fix Version | Story входит в релиз | РП | **Обязательно** |
| Task → Story | `is child of` | Task — часть Story | РП | **Обязательно** |
| Bug → Story | `is caused by` | Bug найден при тестировании Story | Тестировщик | **Обязательно** |
| Bug → Task | `relates to` | Уточнение, в какой Task найден дефект | Тестировщик | Опционально |
| Story → Story | `blocks` / `is blocked by` | Зависимость между историями | РП / Аналитик | По необходимости |
| Task → Task | `relates to` | Техническая зависимость | Разработчик | По необходимости |
| Task → Релиз | — | — | — | **Запрещено** |
| Bug → Релиз | — | — | — | **Запрещено** |
| Bug → Task (без Story) | — | — | — | **Запрещено** |

### 6.2. Базовые правила линковки

1. **Один уровень до релиза.** Релизный тикет «видит» только Story. Всё остальное — через Story.
2. **Story без релиза не попадает в changelog.** Если Story не прилинкована к релизному тикету и не имеет Fix Version — она не войдёт в поставку и не попадёт к ИБ.
3. **Task всегда имеет родительскую Story.** «Сиротская» Task без Story — нарушение процесса; РП обязан исправить в течение рабочего дня.
4. **Bug всегда привязан к Story.** Даже если дефект найден «в конкретной Task» — основной линк идёт на Story; Task указывается в комментарии или опциональном линке `relates to`.
5. **Направление линка важно.** Story — child релиза, Task — child Story, Bug — caused by Story. Не переворачивать направление: релиз не должен быть child Story.
6. **Fix Version дублирует линк.** На каждой Story релиза проставляется Fix Version = версия релиза. Это резервный способ собрать changelog, если линк по какой-то причине потерян.

### 6.3. Какой тип линка когда использовать

| Ситуация | Тип линка | Пример |
|----------|-----------|--------|
| Story входит в релиз | `is child of` → REL | STORY-201 child of REL-100 |
| Task — часть Story | `is child of` → STORY | TASK-301 child of STORY-201 |
| Дефект при тестировании Story | `is caused by` → STORY | BUG-401 caused by STORY-201 |
| Дефект найден в конкретной Task | `relates to` → TASK + `is caused by` → STORY | BUG-401 caused by STORY-201, relates to TASK-301 |
| Story блокирует другую Story | `blocks` | STORY-202 blocks STORY-203 |
| Техническая связь Task | `relates to` | TASK-302 relates to TASK-303 |

**Предпочтительный линк для Bug → Story:** `is caused by` (а не `relates to`). `relates to` — слабая связь, её сложнее отфильтровать в отчётах.

### 6.4. Примеры: правильно и неправильно

#### ✅ Правильно

```
REL-100 (Релиз v2.4.0)
  ├── STORY-201 «Добавить двухфакторную аутентификацию»
  │     ├── TASK-301 «Реализовать TOTP»
  │     ├── TASK-302 «Добавить UI настройки 2FA»
  │     └── BUG-401 «Код не принимается при смене часового пояса»
  └── STORY-202 «Экспорт журнала аудита»
        └── TASK-303 «Добавить endpoint /audit/export»
```

#### ❌ Неправильно

```
REL-100
  ├── STORY-201
  ├── TASK-301          ← Task прилинкован к релизу напрямую
  └── BUG-401           ← Bug прилинкован к релизу напрямую

STORY-202               ← Story без линка к релизу, Fix Version пустой
  └── TASK-302

BUG-402
  └── TASK-303          ← Bug привязан только к Task, без Story
```

### 6.5. Нестандартные ситуации

| Ситуация | Что делать |
|----------|------------|
| **Баг затрагивает несколько Story** | Создать отдельный Bug на каждую Story. Не линковать один Bug к нескольким Story — это ломает отчётность. |
| **Story не вошла в релиз** | РП снимает линк Story → Релиз, очищает Fix Version. Story остаётся в бэклоге для следующего релиза. Task и Bug остаются привязанными к Story. |
| **Story переносится в другой релиз** | РП меняет линк Story: старый релиз → новый релиз. Обновляет Fix Version. Task и Bug переносить не нужно — они следуют за Story. |
| **Hotfix вне планового релиза** | РП создаёт отдельный релизный тикет (например, REL-100-hotfix). Заводит Story на hotfix, линкует к hotfix-релизу. Процесс тот же — только Story в релизе. |
| **Технический долг без Story** | РП заводит Story «Технический долт: …» и линкует к релизу. Task создаётся под Story. Без Story — в релиз не попадает. |
| **Баг найден на production, не связан с текущим релизом** | Тестировщик создаёт Bug → линк к Story, которая изначально внесла функциональность (даже если она в старом релизе). РП решает, включать ли Story-фикс в текущий или следующий релиз. |
| **Story разбита на несколько команд** | Одна Story — один линк к релизу. Task от разных команд — child одной Story. Не дробить Story ради удобства команд, если это одна бизнес-фича для ИБ. |

### 6.6. Правила для ролей при линковке

#### РП

- Проверяет ежедневно (или перед стендапом), что к релизу нет «лишних» линков.
- При заведении Task **сразу** указывает родительскую Story — не откладывает.
- Не допускает Story без Fix Version в активном релизе.
- При переносе Story между релизами — единственный, кто меняет линк Story → Релиз.

#### Аналитик

- Не создаёт Task и Bug — только описывает Story.
- Если видит Task/Bug без Story — эскалирует РП.
- При описании Story указывает, какие компоненты затронуты — это помогает тестировщику правильно линковать Bug.

#### Тестировщик

- При создании Bug **первым действием** — линк `is caused by` к Story.
- В описании Bug указывает: какую Story тестировал, на каком стенде, шаги воспроизведения.
- Не линкует Bug к релизу — даже если дефект блокирует релиз. Блокировка оформляется через приоритет Bug и статус Story.
- Если неясно, к какой Story относится Bug — уточняет у РП/аналитика **до** сохранения тикета.

#### Разработчик

- Не меняет линки Story → Релиз.
- При закрытии Task проверяет, что все связанные Bug в статусе Closed или переданы тестировщику.
- Если обнаружил дефект сам — просит тестировщика завести Bug (разработчик не создаёт Bug самостоятельно, кроме случаев, оговорённых с РП).

### 6.7. JQL-запросы для контроля линковки

**Все Story релиза (для changelog):**
```sql
issue in linkedIssues("REL-100", "is child of") AND type = Story
```

**Task, ошибочно прилинкованные к релизу (нарушение):**
```sql
issue in linkedIssues("REL-100", "is child of") AND type = Task
```

**Bug, ошибочно прилинкованные к релизу (нарушение):**
```sql
issue in linkedIssues("REL-100", "is child of") AND type = Bug
```

**«Сиротские» Task без Story:**
```sql
type = Task AND "Parent Link" is EMPTY AND project = PROJ
```

**Открытые Bug по Story релиза:**
```sql
type = Bug AND status != Closed
  AND issue in linkedIssues(
    issue in linkedIssues("REL-100", "is child of") AND type = Story,
    "is caused by"
  )
```

**Story релиза без заполненного «Влияние на ИБ»:**
```sql
issue in linkedIssues("REL-100", "is child of")
  AND type = Story
  AND "Влияние на ИБ" is EMPTY
```

### 6.8. Рекомендуемая настройка Jira

- Тип **Release** (или Epic «Релиз») — только для релизных тикетов.
- **Issue Link Types:** оставить только используемые (`is child of`, `is caused by`, `blocks`, `relates to`); остальные скрыть из UI, чтобы не путать команду.
- **Automation (при создании линка):** если к релизному тикету линкуют Task или Bug — автокомментарий РП: «Нарушение процесса: к релизу допускаются только Story».
- **Automation (при создании Bug):** если нет линка `is caused by` к Story — перевести Bug в статус «Needs Info» и назначить на тестировщика.
- **Automation (при переводе релиза в «Готов к выкладке»):** проверить JQL нарушений; при наличии — блокировать переход и уведомить РП.
- **Screen Scheme:** на экране Bug поле «Linked Issues» обязательное; подсказка: «Укажите Story, при тестировании которой найден дефект».
- **Dashboard «Здоровье релиза»:** виджеты по JQL из §6.7 — нарушения, открытые Bug, Story без описания ИБ.

## 7. Общие правила процесса

### 7.1. Правила заведения тикетов

| Правило | Описание |
|---------|----------|
| **Одна Story = одна бизнес-ценность** | Story описывает результат для пользователя/бизнеса, а не техническую задачу. «Рефакторинг сервиса X» — Task; «Ускорить отчёт по продажам» — Story. |
| **Story создаёт только РП** | Аналитик и тестировщик не создают Story самостоятельно — запрос к РП. Исключение: шаблонные Story для техдолга по согласованию. |
| **Task создаёт только РП** | Разработчики не создают Task. Если нужна новая Task — запрос РП (или тимлиду → РП). |
| **Bug создаёт только тестировщик** | Разработчик не заводит Bug (кроме оговорённых случаев). Найденный при разработке дефект — через тестировщика или в комментарии к Task. |
| **Релизный тикет — один на версию** | Не создавать несколько релизных тикетов на одну версию. Hotfix — отдельный релизный тикет с суффиксом (`v2.4.1-hotfix`). |

### 7.2. Правила описания

| Тип | Кто описывает | Минимум |
|-----|---------------|---------|
| Релизный тикет | РП | Версия, дата, окружение, список Story (автоматически через линки) |
| Story | Аналитик | Бизнес-цель, критерии приёмки, влияние на ИБ, компоненты, риск |
| Task | РП (или разработчик по шаблону) | Что сделать, оценка, исполнитель |
| Bug | Тестировщик | Шаги воспроизведения, ожидаемый/фактический результат, стенд, скриншот/лог |

**Story нельзя переводить в «Готова к разработке»**, пока аналитик не заполнил блок «Влияние на ИБ». Это обязательное поле для changelog.

### 7.3. Правила статусов и переходов

1. **Story не закрывается, пока открыты Blocker/Critical Bug** с линком `is caused by` на эту Story.
2. **Релиз не переходит в «Готов к выкладке»**, пока хотя бы одна Story релиза не в статусе «Готово к релизу» / Done.
3. **Task закрывается разработчиком** после code review. Тестировщик не закрывает Task.
4. **Bug закрывает тестировщик** после верификации на стенде. Разработчик переводит Bug в «Ready for Test».
5. **Перевод Story в Done** — только РП (или автоматически при закрытии релиза).

### 7.4. Правила работы с changelog для ИБ

1. Changelog формируется **только из Story**, прилинкованных к релизному тикету.
2. Task и Bug **не включаются** в changelog — даже Blocker. ИБ интересует **что меняется в продукте** (Story), а не как это делалось (Task) или что ломалось (Bug).
3. Changelog передаётся ИБ **не позднее чем за 2 рабочих дня** до выкладки в production (срок настраивается под организацию).
4. Если ИБ запрашивает уточнение — аналитик дополняет описание Story, а не создаёт новый тикет.
5. После согласования ИБ РП фиксирует в релизном тикете: дату согласования, ФИО согласовавшего, ссылку на changelog.

### 7.5. Антипаттерны (чего избегать)

| Антипаттерн | Почему плохо | Как правильно |
|-------------|--------------|---------------|
| Линковать Task к релизу «для видимости» | Ломает changelog, ИБ видит лишнее или не видит нужное | Task → Story → Релиз |
| Один Bug на весь релиз | Невозможно понять, какая Story затронута | Bug → конкретная Story |
| Story = Task (один тикет) | Нет разделения бизнес-ценности и работы; ИБ не получает описание | Story + Task под ней |
| Описание ИБ в Task или Bug | Changelog собирается из Story — информация потеряется | Описание ИБ — только в Story |
| «Потом прилинкую» | Забывают, Story не попадает в релиз | Линк и Fix Version — при создании |
| Несколько релизов на одну Story | Story не может быть в двух релизах одновременно | Одна Story — один релиз; перенос — через РП |
| Закрытие Bug без верификации | Дефект уходит в production | Тестировщик верифицирует → Closed |

### 7.6. Эскалация нарушений

| Нарушение | Кто обнаружил | Действие | Срок |
|-----------|---------------|----------|------|
| Task/Bug прилинкован к релизу | РП / Automation | Удалить линк, создать правильный через Story | В тот же день |
| Task без Story | РП / тимлид | РП создаёт Story или привязывает к существующей | 1 рабочий день |
| Bug без Story | Automation / РП | Вернуть тестировщику, дополнить линк | До начала работы над Bug |
| Story без «Влияния на ИБ» | РП перед сборкой changelog | Вернуть аналитику | До передачи changelog ИБ |
| Story не в релизе, но Task в работе | РП | Привязать Story к релизу или остановить Task | В тот же день |

## 8. Статусы (рекомендуемая модель)

### Релизный тикет

`Черновик` → `В работе` → `Готов к выкладке` → `Выкатан` → `Закрыт`

### Story

`Backlog` → `Аналитика` → `Готова к разработке` → `В разработке` → `Тестирование` → `Готово к релизу` → `Done`

### Task

`To Do` → `In Progress` → `Code Review` → `Done`

### Bug

`Open` → `In Progress` → `Ready for Test` → `Closed` / `Won't Fix`

---

## 9. Контрольные точки (чек-лист РП перед релизом)

### Линковка

- [ ] К релизному тикету прилинкованы **только** Story (JQL: нет Task/Bug среди child релиза)
- [ ] У каждой Story в релизе проставлен **Fix Version**
- [ ] Все Task релиза имеют родительскую Story (нет «сирот»)
- [ ] Все Bug релиза имеют линк `is caused by` к Story (нет Bug без Story)
- [ ] Ни одна Story не прилинкована к двум релизам одновременно

### Содержание

- [ ] У каждой Story заполнен блок **«Влияние на ИБ»**
- [ ] У каждой Story заполнены критерии приёмки
- [ ] У каждой Story указан уровень риска

### Готовность

- [ ] Все Task по Story релиза закрыты
- [ ] Нет открытых Blocker/Critical Bug по Story релиза
- [ ] Все Story в статусе «Готово к релизу» / Done

### ИБ

- [ ] Changelog для ИБ сформирован из Story релиза
- [ ] Changelog передан ИБ не позднее установленного срока
- [ ] Получено согласование ИБ (дата и ФИО зафиксированы в релизном тикете)
