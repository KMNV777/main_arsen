# Методика написания тест-кейсов

## 1. Зачем

Тест-кейс — описание одной проверки, которую другой человек выполнит так же, как автор, и получит тот же результат.

## 2. Кейс или чек-лист

| Ситуация | Что использовать |
|---|---|
| Проверка разовая, под одну задачу | Чек-лист: короткие пункты |
| Проверка повторяется (smoke, регресс) | Кейс |
| Проверку будут автоматизировать | Кейс |
| Проверку выполнит не автор | Кейс |

Сомневаетесь — пишите кейс: его легко сократить до пункта чек-листа.

## 3. Структура кейса

| Поле | Что писать |
|---|---|
| Название | «Зона. Действие. Условие → результат» |
| Предусловия | Стенд, версия сборки, роль, состояние данных |
| Данные | Конкретные значения или ссылка на набор |
| Шаги | Нумерованные, одно действие в шаге |
| Ожидаемый результат | Что именно видим или получаем |
| Связь | Ссылка на требование или критерий приёмки |
| Метки | Слой (API, UI), тип (smoke, регресс), важность |

## 4. Правила

1. Одна цель — один кейс. Если в названии есть «и», это два кейса.
2. Один шаг — одно действие и один проверяемый результат.
3. Результат наблюдаем: не «работает правильно», а «отображается сообщение об успехе», «сервис возвращает 403».
4. Кейс независим: нужное состояние создаётся предусловиями, а не результатом другого кейса.
5. Данные, роль и стенд названы явно.
6. До десяти шагов; больше — делите.
7. Негативные и граничные проверки — отдельные кейсы.
8. Перед созданием ищите дубли.
9. Пишите действие в повелительном наклонении («Нажмите»), результат — в изъявительном («Отображается»). Без слов «должен», «примерно», «нормально».
10. Пароли, токены и персональные данные в кейс не пишем.

## 5. Что проверять

| Что проверяем | Приём |
|---|---|
| Поле или параметр с диапазоном | Классы значений и границы: допустимое, недопустимое, минимум, максимум |
| Несколько условий вместе | Таблица комбинаций, кейс на каждую значимую |
| Объект с состояниями | Допустимые и недопустимые переходы |
| Роли и права | Кейс на каждую пару «роль → действие», включая отказ |
| Ключевой пользовательский путь | Один сквозной кейс |

## 6. Пример

**Плохо:** «Открыть форму и проверить, что всё работает → Всё работает». Две цели, нет роли и данных, результат не проверить.

**Хорошо:**

- **Название:** Редактирование формы. Пользователь с правом редактирования сохраняет форму → запись есть в таблице
- **Предусловия:** стенд test, сборка 1234, пользователь с ролью «Редактор», запись №1 в состоянии «Черновик»

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Войдите как «Редактор» | Вход выполнен |
| 2 | Откройте запись №1 | Поля заполнены текущими значениями |
| 3 | Измените «Название», нажмите «Сохранить» | Отображается сообщение об успехе |
| 4 | Откройте запись повторно | В поле «Название» новое значение |

**Парный негативный кейс:** тот же путь под ролью без права редактирования → интерфейс показывает отказ, сервис отвечает 403, значение не изменилось.

## 7. Поддержка

Обновляйте кейс, когда изменились требования или интерфейс, когда кейс падает без дефекта продукта или когда баг прошёл мимо него. Раз в квартал просматривайте набор: убирайте дубли и устаревшие кейсы.

## 8. Чек-лист самопроверки

- [ ] По названию понятно, что и зачем проверяется
- [ ] Предусловия и данные заполнены
- [ ] Один шаг — одно действие
- [ ] Результат наблюдаем, проверяется без автора
- [ ] Нет дубля среди существующих кейсов
- [ ] Указана связь с требованием и метки
- [ ] В кейсе нет секретов
