Методика составления Smoke-проверок — CS2, F2F (TO BE)

Проект CS2, F2F. Команда: QA Lead и три тестировщика. Статус: проект методики, подтверждает QA Lead. Порядок работы, роли и статусы задаёт документ «Регламент тестирования»; ссылки вида «Регламент, раздел 9» указывают на него. Слои проверки и инструменты — в документе «Стратегия тестирования».

1. Назначение и границы

Smoke — короткий проход критичного пути, который отвечает на один вопрос: пригодна ли сборка для дальнейшей проверки и выпуска. Результат бинарный: годна или не годна.

Smoke не ищет все дефекты, не заменяет функциональную проверку задач и регресс. Он быстро показывает, что сборка не сломана на самом важном.

2. Где smoke встречается в процессе

Smoke Когда Кто Что запускается Регламент
Smoke сборки клиента Каждая сборка, раскатанная на test, stage или prod Исполнитель Ручной клиент по чек-листу smoke в TestOps; CI smoke API Шаг 7
Smoke кандидата Номер кандидата известен Исполнитель Ручной клиент и CI smoke API Шаг 19, очередь 1 регресса
Smoke после фикса Новая сборка кандидата Исполнитель CI smoke API и короткий ручной smoke Раздел 9
Smoke критичного пути на stage Кандидат на stage Исполнитель из задачи релиза Чек-лист smoke, критичный путь Шаг 25
Smoke критичного пути на prod Выкладка завершена Исполнитель из задачи релиза Чек-лист smoke, безопасное подмножество Шаг 30

Результат фиксируется закрытым прогоном в TestOps и записью в задаче релиза (для stage и prod).

3. Принципы

  1. Критичный путь. В smoke входит то, без чего продукт не пригоден: доступ, ключевое действие, запись результата, связь клиента и сервисов.
  2. Коротко. Ручной smoke укладывается в 15–30 минут, автоматический smoke API — в минуты (ориентир, фиксируется по базовой линии).
  3. Стабильность. Smoke не содержит нестабильных шагов. Нестабильный шаг лечим или выводим из smoke: красный smoke должен означать дефект, а не шум.
  4. Бинарный итог. Любой красный шаг делает сборку не годной. Решение «частично годна» не принимаем.
  5. Один набор — разные окружения. Набор общий для test, кандидата, stage и prod; для prod используется безопасное подмножество (раздел 8).
  6. Автоматизируем API. Повтор критичного пути не должен зависеть от рук: smoke API запускается из GitLab после сборки.
  7. Растёт только по делу. Новый пункт появляется после пропущенного бага или изменения критичного пути (правило чек-листа доступа и дыр smoke).

4. Как составить чек-лист smoke

Чек-лист smoke хранится в Allure TestOps со ссылкой на схему разработки (Регламент, раздел 4: «критичный путь со ссылкой на схему разработки»).

Шаг Что делаем Результат
1 Взять схему критичного пути у разработки: клиент, сервисы, данные, очередь Список узлов пути
2 Записать ключевые пользовательские сценарии: вход, главное действие, получение результата Сквозной сценарий
3 Разложить сценарий на проверки по узлам: клиент открывается, авторизация, ключевой вызов сервиса, запись данных, отображение результата Кандидаты в smoke
4 Оценить каждого кандидата (раздел 5): влияние, вероятность поломки, стоимость пропуска Ранжированный список
5 Отобрать минимально достаточный набор в рамках лимита времени Черновик чек-листа
6 Назвать входной контроль: версия сборки, доступность стенда, учётные записи Раздел «Перед началом»
7 Задать результат для каждой проверки: что видим, какой код ответа Ожидаемые результаты
8 Отметить слой: ручной клиент, API в CI, один критичный UI-путь Колонка «Слой»
9 Отметить окружения: test, stage, prod; для prod — безопасно ли Колонка «Окружения»
10 Согласовать с разработкой и владельцами зон; ревью Lead Активный чек-лист

5. Отбор проверок в smoke

Критерий Вопрос Вес
Влияние Что теряет пользователь, если шаг сломан? Высокий, если путь блокируется
Вероятность поломки Как часто здесь были дефекты при выкладке? Выше, если были дефекты prod
Стоимость пропуска Сколько стоит дефект на prod? Выше для данных, денег, доступа
Время Сколько занимает проверка? Дорогие проверки в smoke не включаем
Стабильность Можно ли выполнять без шума? Нестабильные не включаем
Независимость Не дублирует ли другой шаг? Дубли убираем

Шаг входит в smoke, если влияние высокое и проверка быстрая и стабильная. Остальное — в риск-регресс или функциональную проверку.

7. Проведение smoke

  1. Входной контроль. Исполнитель сверяет номер сборки с задачей и убеждается, что стенд доступен. Нет сборки или она не по задаче — это возврат по шагу 8 регламента, не результат smoke.
  2. Прогон. Шаги по порядку. Каждая проверка отмечается в прогоне TestOps: пройдено, провалено, заблокировано.
  3. Фиксация. Прогон закрывается в TestOps. Результат smoke кандидата, stage и prod записывается в задаче релиза.
  4. Красный шаг. Заводится Blocker на сборку (регламент: нестабильная сборка), эскалация за 30 минут разработчику зоны и Lead; дальнейшая проверка этой сборки не продолжается.
  5. Новая сборка. После фикса повторяются CI smoke API и короткий ручной smoke; пройденные блоки риск-регресса не перезапускаются, если Lead не сказал иначе.

Результат smoke одним предложением: «Сборка N на test: годна» или «Сборка N на test: не годна, Blocker BUG-123 на шаге 3».

8. Smoke на stage и prod

Требование Stage Prod
Набор проверок Критичный путь целиком Безопасное подмножество
Создание данных Допускается с тестовыми учётками Нет, либо только выделенная тестовая учётка по решению Lead
Изменение данных Допускается Нет
Результат Закрытый прогон в TestOps Результат в задаче релиза, задача релиза закрыта
Красный результат Выпуск не согласуется Откат или исправление по решению руководителя проекта; баг с меткой prod, Lead правит чек-лист

Безопасное подмножество для prod согласуется Lead с руководителем проекта и разработкой до первого использования.

9. Автоматический smoke API

Правило Как
Запуск GitLab CI после сборки и по кнопке на кандидата
Состав Ключевые вызовы критичного пути: авторизация, ключевой сервис, запись
Инструмент Java 17, JUnit 5, REST Assured, Maven
Отчёт Allure на каждый прогон
Красный прогон Владелец зоны теста в тот же день: продукт — баг, тест — фикс теста, инфра — Lead
Ревью QA Lead; кейс отмечается автоматизированным после зелёного прогона
Стабильность Не допускаются ожидания по времени без явных условий и зависимость от порядка

Автотест smoke не заменяет ручной smoke клиента, а дополняет его: клиент проверяется человеком, API — машиной.

10. Сопровождение

Событие Что делаем
Дефект prod прошёл мимо релиза На синке Lead находит дыру в smoke или регрессе и правит чек-лист (Регламент, раздел 11)
Изменился критичный путь Владелец зоны обновляет проверки; ревью Lead
Проверка стала нестабильной Лечим причину, пока лечим — выводим из smoke и записываем в бэклог
Smoke растёт и перестал помещаться во время Убираем пункты с низким влиянием, переносим в регресс
Раз в квартал Lead просматривает чек-лист: дубли, устаревшие шаги, время

11. Типичные ошибки

Ошибка Чем плохо Как исправить
Smoke растёт как регресс Теряется скорость Отбор по разделу 5, лимит времени
Нестабильные шаги в smoke Красный без дефекта, потеря доверия Лечить или выводить
Нет ожидаемых результатов Результат зависит от исполнителя Результат по каждой проверке
Smoke на prod меняет данные Мусор и риск Безопасное подмножество, чтение
Smoke без входного контроля сборки Проверяем не ту сборку Сверка номера сборки с задачей
Нет владельца красного прогона Красное живёт неделями Владелец зоны теста в тот же день

13. Ревью чек-листа

  • ☐ Каждый пункт связан с узлом критичного пути на схеме разработки
  • ☐ Для каждого пункта задан ожидаемый результат
  • ☐ Ручной smoke укладывается в лимит времени
  • ☐ Нет нестабильных шагов
  • ☐ Для prod указано безопасное подмножество
  • ☐ Для каждого автоматизированного пункта есть зелёный прогон в CI
  • ☐ Есть входной контроль сборки и стенда
  • ☐ У чек-листа есть владелец и дата последнего пересмотра
