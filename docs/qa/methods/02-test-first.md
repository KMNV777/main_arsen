# Подход test-first — CS2, F2F (TO BE)

Проект CS2, F2F. Команда: QA Lead и три тестировщика. Статус: проект подхода, подтверждает QA Lead. Порядок работы, роли и статусы задаёт документ «Регламент тестирования»; ссылки вида «Регламент, раздел 7» указывают на него.

## 1. Что такое test-first на CS2

Test-first — это порядок работы, при котором проверка задачи проектируется до реализации, а не после неё. На CS2 подход ограничен тремя уровнями, каждый следующий добавляется только там, где он окупается.

| Уровень | Что появляется до кода | Кто | Обязательность |
|---|---|---|---|
| 1. Проверяемые критерии | Критерии приёмки в форме «дано, действие, результат», каждый можно проверить | Аналитик, вопросы — владелец зоны | Всегда (уже требует регламент) |
| 2. Тестовые идеи и скелет проверок | Список проверок по критериям: чек-лист или черновики кейсов | Исполнитель | Для каждой задачи спринта |
| 3. Автотест до функции | Красный API-тест по контракту, который становится зелёным, когда функция готова | Автор автотестов API (Middle+ или Senior) | Для задач с API и расчётами, где есть контракт |

Подход не заменяет юнит-тесты разработчиков и не делает из тестировщика разработчика: тестировщик не пишет код продукта, а задаёт проверяемое определение готовности.

## 2. Зачем

- Критерий, который нельзя проверить, находят до разработки, а не на шаге 8 передачи (в регламенте такая задача возвращается аналитику).
- Разработчик видит, чем задача будет проверяться, и делает самопроверку по тем же критериям.
- Меньше возвратов на передаче и меньше переоткрытых багов.
- Проверка не подстраивается под готовую реализацию: тест не пишется «под то, что получилось».

## 3. Когда применять, когда нет

| Применяем | Не применяем или упрощаем |
|---|---|
| Изменение API или контракта сервиса | Правки вёрстки без логики (достаточно уровня 1 и сверки с макетом) |
| Расчёты, правила, проверка прав | Исследовательские задачи без критериев (сначала спайк) |
| Исправление бага: воспроизводящий тест до фикса | Разовые правки конфигурации стенда |
| Задачи критичного пути | Задачи, где нет стабильного контракта или стенда для автотеста |

Для UI-логики на клиенте достаточно уровней 1 и 2. Автотест UI до функции не пишем: UI в автоматизации — один критичный путь на Selenium 4.

## 4. Процесс по шагам

Шаги привязаны к нумерации регламента (Регламент, раздел 12).

| Шаг | Что делаем | Кто | Результат |
|---|---|---|---|
| Шаг 3 регламента | Аналитик пишет критерии приёмки по шаблону «дано, действие, результат», до семи критериев | Аналитик | Задача по шаблону DoR |
| Тестирование требований | Исполнитель проверяет критерии по списку вопросов из раздела 5 | Исполнитель | Вопросы комментарием в задаче |
| Шаг 4 регламента (груминг) | Владелец зоны задаёт вопросы к критериям; ответы фиксируются в задаче | Владелец зоны | Вопросов нет или все отвечены |
| Шаг 5 регламента (после груминга) | Исполнитель составляет тестовые идеи по критериям и оценивает проверку | Исполнитель | Список проверок в Story, оценка в поле «Оценка тестирования» |
| Уровень 3 (для API-задач) | Автор автотестов пишет API-тест по контракту (Swagger, требования); тест красный | Автор автотестов API | Merge request с красным тестом, ссылка в задаче |
| Шаг 6 регламента | Разработчик реализует функцию, прогоняет свой тест и самопроверку, ставит «Готово к тестированию» | Разработчик | Зелёный тест, сборка на test |
| Шаги 7–10 регламента | Smoke сборки, проверка по списку проверок, дефекты | Исполнитель | Чек-лист или кейсы закрыты |

**Оценка.** Работа по уровням 2 и 3 входит в «Оценку тестирования» задачи. Для задач с автотестом до функции оценка выделяется в подзадачу [QA] (Регламент, раздел 7.4).

## 5. Уровень 1: проверка требований

Список вопросов, который исполнитель применяет к каждому критерию.

| Вопрос | Если ответ «нет» |
|---|---|
| Критерий однозначен: два человека поймут одинаково? | Вопрос аналитику комментарием |
| Есть начальное состояние («дано»)? | Вопрос: в каком состоянии система и данные |
| Есть конкретное действие? | Вопрос: что делает пользователь или система |
| Результат наблюдаем: что видит пользователь, что вернул сервис, что лежит в таблице? | Вопрос: как проверить |
| Критерий можно закрыть одной проверкой? | Предложить разбить |
| Критерии не противоречат друг другу и требованиям? | Вопрос с указанием пары |
| Учтены роли и права, включая отказ? | Вопрос: что видит пользователь без права |
| Учтены граничные значения и ошибки? | Вопрос: что при пустом, максимальном, неверном значении |
| Описаны зависимости и миграции? | Вопрос разработчику |

Критерий, который нельзя проверить, возвращает задачу (Регламент, раздел 7.3). Пример переформулировки:

- Было: «Кнопка работает правильно».
- Стало: «Пользователь с правом редактирования сохраняет форму. Запись появляется в названной таблице. Повторное открытие показывает те же значения. Пользователь без права сохранение не выполняет: интерфейс показывает отказ, сервис отвечает 403».

## 6. Уровень 2: тестовые идеи

Исполнитель после груминга оформляет в Story блок «Проверки»: по каждому критерию одна или несколько строк.

| Критерий | Проверка | Тип | Слой | Автоматизация |
|---|---|---|---|---|
| 1 | Сохранение формы пользователем с правом | Позитив | API | Да, до функции |
| 1 | Сохранение формы пользователем без права: 403, значение не изменилось | Негатив | API | Да, до функции |
| 2 | Граничные значения поля «Название» | Граничные | API | Кандидат |
| 3 | Отображение результата на экране | Сверка с макетом | UI | Нет |

Блок «Проверки» затем превращается в чек-лист Story или в кейсы TestOps по методике оформления тест-кейсов. Блок согласуется с аналитиком, если вопросы к критериям остались.

Для техник выбора проверок см. методику оформления тест-кейсов, раздел 5.

## 7. Уровень 3: автотест до функции

Условия: есть контракт (Swagger или описание в требованиях), стенд test, автор автотестов с грейдом Middle+ или Senior, ревью QA Lead.

1. Автор пишет тест на JUnit 5 и REST Assured по критерию. Тест вызывает endpoint по контракту и проверяет код ответа и поля ответа.
2. Тест запускается на стенде и красный: функции ещё нет или она не по контракту.
3. Автор прикладывает merge request и ссылку на тест к задаче; кейс в TestOps остаётся в статусе «на ревью» или «активный» без отметки «автоматизирован».
4. Разработчик реализует функцию, прогоняет тест локально и на test в рамках самопроверки.
5. Тест становится зелёным в CI. Только после этого кейс помечается автоматизированным (правило регламента, раздел 6).
6. Если контракт изменился при реализации, меняются и критерий, и тест; изменение фиксируется комментарием в задаче.

Пример заготовки (условный):

```java
@AllureId("1234")
@DisplayName("Редактирование формы: пользователь без права получает 403")
@Epic("Формы")
@Feature("Редактирование")
@Severity(SeverityLevel.CRITICAL)
@Tag("api")
@Test
void viewerCannotSaveForm() {
    given().auth().oauth2(viewerToken())
        .body(updateBody("Новое название"))
        .when().put("/forms/{id}", formId)
        .then().statusCode(403);
}
```

Красный тест на этом шаге ожидаем. Он не блокирует сборку кандидата, потому что живёт в ветке задачи и не входит в CI smoke до готовности функции.

## 8. Багфикс test-first

1. Баг воспроизводится на сборке; шаги и условия записаны в баг-репорте.
2. Исполнитель или автор автотестов оформляет воспроизводящую проверку: кейс или автотест, который красный на сборке с багом.
3. Разработчик исправляет, проверка становится зелёной, статус «Исправлен» с номером сборки.
4. Исполнитель делает ретест и короткий проход вокруг. Проверка остаётся в наборе: она ловит повтор бага.

Для Blocker и Critical воспроизводящая проверка добавляется в риск-регресс (если баг найден в регрессе) или в блок зоны (если вне регресса).

## 9. Роли и ответственность

| Роль | Что делает в test-first |
|---|---|
| Аналитик | Пишет проверяемые критерии, отвечает на вопросы до разработки |
| Владелец зоны | Задаёт вопросы к критериям на груминге |
| Исполнитель | Проверяет критерии, составляет тестовые идеи и оценку |
| Автор автотестов API | Пишет красный тест до функции |
| Разработчик | Реализует функцию, прогоняет тесты, делает самопроверку |
| QA Lead | Ревьюит автотесты, ведёт метрики подхода, решает, где подход применять |

## 10. Анти-паттерны

| Анти-паттерн | Почему плохо | Что делать |
|---|---|---|
| Тест пишется по готовой функции «как получилось» | Теряется смысл независимой проверки | Писать по критерию и контракту |
| Критерии «внутри головы» аналитика | Нельзя проверить | Вопрос в задаче, возврат на шаг 3 |
| Красный тест в общей ветке | Ломает CI | Тест в ветке задачи, включение в CI после зелёного прогона |
| Тест на каждую мелочь до функции | Раздувает сопровождение | Только критерии с API-контрактом и расчёты |
| Тест-идеи не согласованы с аналитиком | Расхождение в понимании | Показать блок «Проверки» аналитику |
| Подход ради подхода на всех задачах | Тормозит спринт | Раздел 3 про применимость |

## 11. Метрики подхода

Используются стандартные метрики стратегии: возвраты при передаче, покрытие требований (критерии, закрытые проверкой), reopen rate, раннее выявление дефектов, точность оценки.

Дополнительно на пилоте считаются: доля задач спринта с блоком «Проверки» до «Готово к тестированию»; доля API-задач с автотестом до функции; число критериев, переформулированных на тестировании требований.

## 12. Внедрение

1. **Пилот на два спринта.** Выбрать две-три API-задачи и одну задачу без API. Уровни 1 и 2 — на всех задачах пилота; уровень 3 — на API-задачах.
2. **Измерить.** Возвраты на шаге 8, reopen rate, время от «Готово к тестированию» до «Готово», затраты на подготовку.
3. **Решить на синке.** Расширить на все API-задачи, оставить только уровни 1 и 2 или отказаться от уровня 3.
4. **Зафиксировать в регламенте.** После подтверждения добавить шаг «Проверки до кода» в процесс по шагам.
