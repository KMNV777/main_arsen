# Методика анализа багов — CS2, F2F (TO BE)

Проект CS2, F2F. Команда: QA Lead и три тестировщика. Статус: проект методики, подтверждает QA Lead. Порядок работы, роли, серьёзность и статусы задаёт документ «Регламент тестирования»; ссылки вида «Регламент, раздел 8» указывают на него. Метрики и реестр рисков — в документе «Стратегия тестирования».

## 1. Назначение и границы

Методика описывает, как исполнитель и Lead разбирают дефект от момента обнаружения до выводов по команде: локализация, оформление, триаж, ретест, анализ причин пропуска и анализ трендов.

Шаблон баг-репорта, серьёзность, статусы, сроки эскалации и правило «баг старше 30 дней» живут в регламенте и здесь только применяются.

## 2. Уровни анализа

| Уровень | Вопрос | Кто | Когда |
|---|---|---|---|
| 1. Локализация | Что сломано, где и при каких условиях | Исполнитель | При обнаружении |
| 2. Оформление и триаж | Как серьёзно, чей, чинить ли сейчас | Исполнитель, владелец зоны, владелец продукта | При заведении и на груминге |
| 3. Ретест и анализ фикса | Исправлено ли, не сломали ли вокруг | Исполнитель | Статус «Исправлен» |
| 4. Анализ пропуска | Почему дефект дошёл до prod или регресса | QA Lead | Дефект prod, Blocker или Critical вне регресса |
| 5. Анализ трендов | Где и почему дефектов больше | QA Lead | Спринт, релиз, квартал |

## 3. Уровень 1: локализация

### 3.1 Порядок

1. **Воспроизвести.** Повторить минимум дважды. Если не воспроизводится — записать условия и число попыток.
2. **Минимизировать шаги.** Убрать всё лишнее, оставить кратчайший путь к дефекту.
3. **Зафиксировать условия.** Сборка, стенд, роль, данные, браузер или устройство, время.
4. **Определить слой.** Клиент, сервис, данные, интеграция (очередь, чужой сервис), окружение.
5. **Собрать вложения.** Видео или скрин, лог клиента, консоль, лог сервиса, запрос и ответ.
6. **Проверить границы.** Зависит ли от роли, данных, сборки, стенда; воспроизводится ли на другой сборке (до или после).
7. **Искать среди открытых.** Перед заведением — поиск дублей по зоне и симптому.

### 3.2 Куда смотреть по симптому

| Симптом | Первое, что проверить | Инструмент |
|---|---|---|
| Клиент не загружается или зависает | Номер сборки, консоль браузера, статус-коды ресурсов | DevTools: Console, Network |
| Действие не выполняется | Запрос и ответ сервера, код ответа | DevTools: Network, Postman, Swagger |
| Ошибка 4xx | Параметры запроса, права, авторизация | Postman, ответ сервиса |
| Ошибка 5xx | Лог сервиса в момент запроса | Grafana, если журнал стенда подключён |
| Данные не совпадают | Что лежит в базе и что показывает клиент | SQL-клиент (DBeaver, DataGrip), SELECT с JOIN |
| Сообщение не дошло | Прохождение по очереди: отправитель, брокер, получатель | Логи, брокер сообщений (Kafka, RabbitMQ) |
| Работает у одной роли, не работает у другой | Права и конфигурация ролей | Сравнение запросов под разными ролями |
| Только на одном стенде | Версия сборки, конфигурация, данные | Сравнение стендов |
| Не воспроизводится стабильно | Гонки, таймауты, зависимость от данных, сеть | Повтор с логами, сниффер (Fiddler, Charles) |
| Регресс: раньше работало | Какая сборка последняя «хорошая» | Сборка до и после, список изменений |

### 3.3 Вложения

| Тип | Когда обязателен |
|---|---|
| Видео или скрин | Всегда для клиента |
| Лог клиента или консоль | Ошибки клиента |
| Запрос и ответ | Ошибки API |
| Лог сервиса или ссылка на Grafana | Подозрение на сервис |
| Номер сборки | Всегда для клиента |

## 4. Уровень 2: оформление и триаж

### 4.1 Баг-репорт

Поля по регламенту, раздел 8: Summary, Description, Вложения, Environment, Sprint, Regression, Component, Severity.

**Формула Summary:** «Зона. Что сломано, где, на каком действии». Пример (условный): «Формы. Не сохраняется значение «Название» в карточке записи при нажатии «Сохранить»».

**Формула Description:**

1. Шаги воспроизведения, пронумерованные.
2. Ожидаемый результат (из критерия приёмки, требования или макета, а не «из вкуса»).
3. Фактический результат.
4. Условия: сборка, стенд, роль, данные.
5. Кто нашёл, когда.
6. Как часто воспроизводится.

**Плохой баг-репорт** (условный): «Форма не работает. Проверьте». Нет зоны, шагов, результата, сборки.

**Хороший баг-репорт** (условный):

| Поле | Значение |
|---|---|
| Summary | Формы. Не сохраняется «Название» в карточке записи при нажатии «Сохранить» |
| Description | 1. Авторизоваться как «Редактор». 2. Открыть запись №1. 3. Изменить «Название», нажать «Сохранить». Ожидал: значение сохранено (критерий 2 STORY-123). Получил: интерфейс показывает успех, при повторном открытии старое значение. Воспроизводится 3 из 3 |
| Вложения | Видео, запрос и ответ (PUT вернул 200 без изменения), лог сервиса |
| Environment | test, сборка 1234 |
| Component | Формы |
| Regression | Нет |
| Severity | Major |

### 4.2 Серьёзность и приоритет

Серьёзность определяется по таблице регламента (Blocker, Critical, Major, Normal, Minor). Исполнитель не подстраивает серьёзность под приоритет: серьёзность — свойство дефекта, приоритет после создания может сменить владелец продукта.

Алгоритм выбора серьёзности:

| Вопрос | Ответ | Серьёзность |
|---|---|---|
| Можно ли пройти критичный путь или открывается ключевой модуль? | Нет | Blocker |
| Сломан ли рабочий сценарий без обхода? | Да | Critical |
| Сломан ли сценарий, но есть обход? | Да | Major |
| Дефект есть, но под правила выше не подходит? | Да | Normal |
| Портит удобство, сценарий не ломает? | Да | Minor |

Пограничные случаи: сомнение между двумя серьёзностями решается в сторону большей; спор фиксируется комментарием, решение принимает QA Lead.

### 4.3 Дубли и связанные дефекты

- Перед заведением ищем по зоне, симптому и тексту ошибки.
- Дубль закрывается ссылкой на основной баг.
- Баг с общей причиной связывается ссылкой related.
- Метка Regression = Да ставится, если сценарий раньше работал, входит в регресс или найден в регрессе.

### 4.4 Триаж

| Решение | Кто принимает | Результат |
|---|---|---|
| Чиним в спринте | Владелец зоны (Normal, Minor), владелец продукта (Major) | Баг в спринте, срок фикса комментарием |
| В бэклог | Те же | Метка backlog и решение комментарием |
| Не баг | Владелец зоны | Закрыт с объяснением |
| Блокер или Critical | Нашедший эскалирует за 30 минут (Blocker) или 2 часа (Critical, в регрессе — 30 минут) | Разработчик зоны и QA Lead |

Блок «Выход из проверки» регламента: Major в бэклоге — с комментарием владельца продукта, Normal и Minor — владельца зоны.

## 5. Уровень 3: ретест и анализ фикса

1. Разработчик делает самопроверку и ставит «Исправлен» с номером сборки.
2. Исполнитель проверяет, что сборка содержит фикс.
3. Повторяет шаги из баг-репорта.
4. Проверяет граничные варианты и соседние сценарии («проход вокруг»).
5. Принимает решение:

| Результат | Действие |
|---|---|
| Баг не воспроизводится, вокруг чисто | Статус «Закрыт» (Blocker закрывается после ретеста исполнителем; Critical — с согласия нашедшего и QA Lead) |
| Тот же сценарий и та же причина воспроизводятся | «Переоткрыт» |
| Найден другой дефект или другая причина | Новая задача со связью related, исходный баг закрывается |

Анализ фикса: фикс закрыл симптом или причину? Добавлена ли воспроизводящая проверка (кейс или автотест) для Blocker, Critical и Major — см. подход test-first, раздел 8.

## 6. Уровень 4: анализ пропуска

Запускается для: дефекта с меткой prod; Blocker или Critical, найденного вне регресса; дефекта, который прошёл через регресс.

### 6.1 Вопросы

| Вопрос | Варианты ответа |
|---|---|
| Где дефект должен был быть найден? | Требования и критерии, ревью кода, функциональная проверка, smoke, регресс, автотест, stage или демо |
| Почему не найден? | Нет критерия; нет кейса; кейс был, но не вошёл в срез; кейс был нестабильным; стенд или данные отличались; не было сборки; проверка не доехала по времени |
| Что в нашей зоне контроля? | Чек-лист smoke, кейсы регресса, автотесты, критерии, данные |
| Что меняем? | Пункт в smoke; кейс в регресс; критерий в DoR; автотест; правило отбора регресса; данные или стенд |
| Кто и к какому сроку? | Владелец и срок |

### 6.2 Шаблон записи

| Поле | Что писать |
|---|---|
| Баг | Ссылка |
| Описание | Одно предложение: что случилось у пользователя |
| Где пропущен | Этап процесса |
| Почему пропущен | Причина по классификатору (раздел 8) |
| Корректирующее действие | Что меняем |
| Владелец и срок | Фамилия, дата |
| Проверка | Как проверим, что действие сработало |

Запись делает QA Lead на синке и оставляет в баге комментарием. Правка чек-листа smoke или регресса (Регламент, раздел 11) входит в корректирующее действие.

### 6.3 Метод «пять почему»

Для дефектов с высоким влиянием на синке разбираем цепочку: симптом → почему не поймали → почему не было проверки → почему не было критерия или кейса → что меняем в процессе. Цель — действие, а не виновник.

## 7. Уровень 5: анализ трендов

| Срез | Вопрос | Метрика |
|---|---|---|
| По компонентам | Где дефектов больше всего | Распределение дефектов по компонентам |
| По серьёзности | Растёт ли доля серьёзных | Открытые дефекты по серьёзности |
| По причинам | Откуда берутся дефекты | Классификатор причин (раздел 8) |
| По этапу обнаружения | Что мы ловим раньше, что позже | Раннее выявление, Defect Detection Percentage |
| По утечке | Сколько дошло до prod | Defect Leakage |
| По переоткрытиям | Качество фиксов | Reopen rate |
| По возрасту | Что висит в бэклоге | Баги старше 30 дней |
| По времени | Как быстро чиним | Время исправления |

### Ритм

| Период | Что делаем |
|---|---|
| Синк (раз в неделю) | Открытые Blocker и Critical, баги старше 30 дней, дефекты prod; для каждого — решение |
| Конец спринта | Reopen rate, распределение по компонентам, самые частые причины |
| Релиз | Дефекты регресса, утекшие, найденные в спринте до заморозки |
| Квартал | Отчёт по дефектам (структура ниже), изменения в чек-листах и регрессе |

### Структура квартального отчёта по дефектам

1. Сводка: число дефектов по серьёзности, доля prod.
2. Топ-3 компонента по числу дефектов и по серьёзности.
3. Топ причин по классификатору.
4. Пропуски: что и почему прошло, какие действия выполнены.
5. Тренды: Defect Leakage, reopen rate, время исправления.
6. Что меняем в smoke, регрессе, критериях, автотестах.

## 8. Классификатор причин дефектов

Причина записывается в баге после исправления (поле или метка в Jira; решение на подтверждение).

| Причина | Что значит |
|---|---|
| Требования | Нет, неполные или противоречивые требования и критерии |
| Реализация | Ошибка в коде зоны |
| Интеграция | Несогласованность клиента, сервисов, очереди, контракта |
| Данные и миграции | Данные в нужном состоянии отсутствуют или миграция сломала |
| Конфигурация и окружение | Настройки, стенд, версии |
| Сборка и выкладка | Сборка не та, не раскатана, неполная |
| Доступ и права | Роли, авторизация, формы |
| Автотест или кейс | Ошибка в самом тесте, а не в продукте |
| Чужой сервис | Дефект вне поставки команды |
| Не воспроизводится или не баг | Закрыт без исправления |

Причина «Автотест или кейс» и «Не баг» не считаются в утечку и метриках дефектов продукта.

## 9. Бэклог и старые баги

| Ситуация | Действие |
|---|---|
| Баг в бэклоге старше 30 дней без движения | Lead выносит на синк: закрыть, починить или явно оставить |
| Баг не воспроизводится месяц | Закрываем с комментарием «не воспроизводится» |
| Нескольких багов общая причина | Связать related, взять в одну задачу |
| Major в бэклоге | Комментарий владельца продукта обязателен |

## 10. Роли

| Роль | Что делает |
|---|---|
| Исполнитель | Локализует, оформляет, проверяет фикс, закрывает; не подстраивает серьёзность под приоритет |
| Разработчик зоны | Исправляет, самопроверяет, пишет срок фикса для Blocker и Critical |
| Владелец зоны | Решает по Normal и Minor, разбирает красные автотесты |
| Владелец продукта | Решает по Major, приоритет |
| QA Lead | Ведёт анализ пропусков и трендов, правит чек-листы, выносит старые баги на синк |
| Руководитель проекта | Решает по срокам при угрозе дате |

## 11. Типичные ошибки

| Ошибка | Чем плохо | Как исправить |
|---|---|---|
| Баг без шагов и результата | Не воспроизводится | Шаблон Description |
| Серьёзность «под приоритет» | Искажаются метрики и решения | Алгоритм раздела 4.2 |
| Дубли без поиска | Шум, путаница | Поиск по открытым перед заведением |
| Переоткрытие вместо нового дефекта | Смешиваются причины | Правило раздела 5 |
| Анализ пропуска ради виноватого | Люди скрывают пропуски | Цель — корректирующее действие |
| Нет причины после фикса | Нечего анализировать в трендах | Классификатор причин |
| Баги висят в бэклоге | Теряется доверие | Просмотр на синке, 30 дней |

## 12. Чек-лист качества баг-репорта

- [ ] Summary в формате «Зона. Что сломано, где, на каком действии»
- [ ] Есть поиск по открытым, дублей нет
- [ ] Шаги нумерованы, воспроизводятся без автора
- [ ] Ожидаемый результат ссылается на критерий, требование или макет
- [ ] Фактический результат описан без оценок
- [ ] Указаны сборка, стенд, роль, данные
- [ ] Вложения: видео или скрин, лог, запрос и ответ
- [ ] Серьёзность по алгоритму, Component одна, Regression указан
- [ ] Для Blocker и Critical есть эскалация в срок

## 13. Метрики и связь с регламентом

Используются стандартные метрики стратегии: Defect Leakage, Defect Detection Percentage, открытые дефекты по серьёзности, распределение дефектов по компонентам, возраст дефектов, reopen rate, время исправления. KPI по багам на человека не применяются.

| Что | Где в регламенте |
|---|---|
| Серьёзность, поля баг-репорта, новые дефекты на ретесте | Раздел 8 |
| Эскалация Blocker и Critical | Раздел 11 |
| Статусы бага | Раздел 7.1 |
| Дефект в prod после выпуска | Раздел 11 (исключения) |
| Баги старше 30 дней | Раздел 8, синк |

## 14. Решения на подтверждение

| Решение | Кто подтверждает |
|---|---|
| Классификатор причин дефектов и поле или метка в Jira | QA Lead, администратор Jira |
| Шаблон записи анализа пропуска и разбор на синке | QA Lead |
| Квартальный отчёт по дефектам | QA Lead, руководитель проекта |
| Таблица быстрой локализации по симптомам (раздел 3.2) как стандарт | QA Lead |
