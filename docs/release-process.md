# Процесс ведения релиза: регламент и реестр шагов

> Схема: [`drawio/10-release-process.drawio`](drawio/10-release-process.drawio) (4 страницы). Превью стр. 1: [`svg/10-release-process-1.svg`](svg/10-release-process-1.svg). Файл генерируется скриптом `scripts/build_release_process.py` — правим данные в скрипте, не руками в XML.

## Цели

1. Прозрачно показать **параллельные и последовательные** действия цикла релиза (параллельный блок P: треки A/B/C, стык на шлюзе G1).
2. Каждый шаг = подзадача Jira → время работы и ожидания по этапам собирается автоматически.
3. Чётко разделить **зоны ответственности** (дорожки) и закрепить ответственного за каждым шагом.
4. Видеть, **где, кем и на каком шаге** допущены ошибки, где систематически ошибаемся в оценке и где нарушаются требования.
5. **Сервис** — часть процесса: он указан в заголовке каждой страницы схемы, в релиз-тикете и в каждой подзадаче; матрица «сервис × этап» показывает качество прохождения по каждому сервису.

## Ветки и отбор задач

Полная схема — страница 2. Кратко:

- `master` = состояние Прода; прямые коммиты запрещены.
- `release/<сервис>/<версия>` режется от master **после** фиксации скоупа (0.2), SHA записывается в тикет.
- В ветку вливаются только задачи из скоупа (MR, ревью ✓, CI ✓, dev-тест ✓). Не вливаются: без dev-теста, с зависимостью вне скоупа, миграции без отката, ПСИ без ПМТ, принятые после фриза без согласия RM.
- После фича-фриза — только fix crit/blocker; код-фриз фиксирует hash, по которому идут smoke, аудит ИБ и релиз-борд.
- После стабильного Прода: тег, merge release → master, back-merge (5.4).

## Jira-модель

- **Релиз-тикет** `REL-<сервис>-<версия>`: Сервис*, Направление*, Версия*, release-ветка, master@SHA, hash код-фриза, psi_required, Скоуп, решения G1/G2.
- **Подзадача «Этап релиза»** на каждый шаг: ID шага*, Сервис*, Роль, Исполнитель, План ч*, Старт, Готово, Результат, Код ошибки, Этап внесения, «Возврат из».
- Workflow: Ожидает → В работе → Готово. Возврат = новая подзадача того же шага + ссылка на шаг-источник + код ошибки.

## Таксономия ошибок

| Код | Тип | Что фиксируем |
|---|---|---|
| E1 | Ошибка скоупа | Задача включена/исключена неверно; добавлена после фриза; расхождение «скоуп ↔ ветка» |
| E2 | Ошибка оценки | Факт отличается от плана более чем на порог (предлагается 25 %); недооценён объём регресса или фиксов |
| E3 | Нарушение регламента | Пропущен шаг или не выполнен критерий входа/выхода; нет данных в тикете |
| E4 | Дефект кода | Дефект внесён на этапе X, найден на этапе Y (фиксируем оба этапа) |
| E5 | Окружение / сборка / выкат | Сбой стенда, сборки, миграции, деплоя |
| E6 | Простой / ожидание | Ожидание ответа, ресурса или решения сверх согласованного SLA шага |
| E7 | Внешняя зависимость | Время и возвраты на стороне ИБ ГПН-ЦР / ГПН-ЦР — фиксируем фактами, а не ощущениями |

## Метрики

| № | Метрика | Расчёт | Срезы |
|---|---|---|---|
| M1 | Время работы шага | Готово − Старт (рабочие часы) | шаг · сервис · исполнитель |
| M2 | Ожидание перед шагом | Старт − max(Готово предшественников); для P — от fork | шаг · ЗО · сервис |
| M3 | Длительность релиза и критический путь | Σ(работа + ожидание) по самой длинной цепочке; доля по ЗО (НЕДРА / ИБ / ГПН-ЦР) | сервис · релиз |
| M4 | Точность оценки | (Факт − План) / План; смещение = медиана по роли/шагу | роль · шаг · сервис |
| M5 | FPY — прохождение с первого раза | доля шагов без возврата | шаг · сервис |
| M6 | Возвраты | число и время повторов; матрица «внесено на X → найдено на Y» | шаг-источник · шаг-приёмник |
| M7 | Нарушения требований | число E3 на шаг; невыполненные критерии входа/выхода | шаг · сервис · исполнитель |
| M8 | Churn скоупа | доля задач, добавленных после фриза / исключённых из релиза | сервис · релиз |

## Допущения и открытые вопросы

- Названия сервисов и направлений не заданы — в схеме плейсхолдеры (`SERVICES`, `META` в скрипте).
- Шаги, помеченные ★ (0.2, 1.1–1.3, G2, 5.3–5.5), предложены как недостающие в прежней схеме — нужно подтвердить.
- Заявка на аудит (2.6) в прежней схеме шла после регресса; здесь она подаётся после скана на фризе, чтобы аудит шёл параллельно регрессу. Подтвердить.
- Регресс PreProd (4.2) оставлен за RM, как на прежней схеме; возможно, его стоит передать QA.
- Плановые нормативы времени (SLA шагов) пока не заданы — нужны для метрики M2/E6.
- ФИО исполнителей на шагах БД и брокеров прочитаны со скана схемы — проверить.
