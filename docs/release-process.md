# Процесс выпуска релиза ЕАРМ — итоговая редакция

> Схемы: [`drawio/10-release-process.drawio`](drawio/10-release-process.drawio) (4 страницы: процесс, ветки, дорожная карта, Jira и метрики). Единый отчёт для ревью — [`release-process-full.html`](release-process-full.html). Файлы генерирует `scripts/build_release_process.py`.

## Принятые решения

- Ветка — от master на старте спринта; допускается несколько веток параллельно. Фича-фриз — в конце спринта; не успели — в следующий релиз (спринт). Scope freeze нет.
- Демо проводит QA, принимает ВНП.
- Релиз-борд: аудит → выкатка на UAT → функциональное тестирование → ПСИ ИБ → согласование трансфера на ПРОД (ЗО релиз-инженера НЕДРА).
- Go/No-Go нет; критические дефекты — в hotfix; hotfix — тот же процесс.
- Smoke PROD, БД и брокеры — параллельно.

## Описание этапов

**1. Приоритеты бэклога** — 1 дн.. ВНП направления сообщает приоритеты бэклога и бизнес-требований на спринт.

**2. Оценка задач и планирование спринта** — 1 дн.. РП направления вместе с командой оценивает задачи и формирует состав спринта с учётом ёмкости ролей. Ёмкость QA считается за вычетом резерва на регресс и Smoke предыдущего релиза (см. «Стратегическое планирование»).

**3. Сбор релизного тикета** — 1 дн.. Release owner собирает релизный тикет (Fix Version) из оценённых задач: только Story и Bug с оценкой, тест-кейсами и скриптами миграции; заводит строку в календаре и паспорт релиза.

**4. Подтверждение состава релиза** — 1 дн.. ВНП направления подтверждает состав релизного тикета: что должно войти в релиз. После подтверждения стартует спринт.

**5. Разработка и влитие задач в master** — в течение спринта. Мейнтейнеры вливают закрытые задачи в master своего сервиса (у каждого сервиса свой репозиторий): PR с ревью, ссылкой на ключ Story, кодовым инкрементом и скриптами миграции. Незавершённое — за feature flag; сложные фичи — в опциональную агрегирующую (супер-фича) ветку, которая вливается в master целиком после приёмки.

**6. Скан и устранение уязвимостей в CI** — в течение спринта. SAST, SCA, Luntry и проверка секретов запускаются в CI на каждый PR; blocker и critical устраняются в спринте — это условие готовности задачи (Релизная политика, правило 6).

**7. Тестирование задач и исправление багов спринта** — в течение спринта. QA тестирует влитые задачи на UAT по ходу спринта, найденные баги правятся в этом же спринте; задачи без тест-кейсов в релиз не попадают.

**8. Release notes и changelog** — в течение спринта. Технический писатель по закрытым задачам готовит release notes и changelog к фича-фризу: к моменту подготовки TOML они уже должны быть готовы.

**9. Демо и приёмка задач** — 1 дн.. QA проводит демо закрытых задач, ВНП принимает их.

**10. Вывод не принятых задач из релиза** — в день демо. Если задачу не приняли на демо, её убирают из релиза до тега: revert PR либо отключение feature flag, супер-фича-ветка не вливается. Fix Version снимается, задача переносится в следующий релиз.

**11. Фича-фриз и тег релиза** — в последний день спринта. В последний день спринта новые фичи в релиз не принимаются; на коммит master в репозитории каждого сервиса ставится защищённый (protected) git-тег с ID релиза (например, EARM26.4.1). Всё, что не успели, — в следующий релиз = следующий спринт.

**12. Регресс на UAT** — 3 дн.. Регрессионное тестирование тега релиза по тест-плану из ТестОпс НЕДРА с приоритетом по риску (миграции БД, брокеры, интеграции между сервисами, критичные потоки), контрактные проверки между сервисами, заведение дефектов с критичностью, отчёт о регрессе.

**13. Финальный скан по тегу релиза (CI)** — 3 дн.. Контрольный прогон SAST, SCA, Luntry и секретов по тегу релиза. Основная работа с уязвимостями идёт в спринте; здесь проверяется, что блокеров не осталось.

**14. Подготовка TOML** — 2 дн.. Release owner готовит TOML-файл релиза: ссылки на готовые release notes и changelog, digest образов, порядок выката и совместимость версий сервисов, обязательный план отката (включая миграции БД); архитектор проводит ревью. TOML нужен для инициации релиз-борда.

**15. Импорт тест-плана в ТестОпс ГПН-ЦР** — 1 дн.. QA финализирует тест-план, Release owner импортирует его в ТестОпс ГПН-ЦР для регресса на PreProd.

**16. Устранение багов и уязвимостей после регресса** — 3 дн.. Мейнтейнеры исправляют дефекты регресса и блокирующие находки финального скана: в master, а если в master уже есть изменения следующего спринта — в короткоживущую ветку от тега релиза. Ставится итоговый защищённый тег — код-фриз. Распределение багов по разработчикам — РП направления.

**17. Smoke UAT** — 2 дн.. QA проверяет работоспособность итогового тега на UAT; готовность сборки — рекомендация QA.

**18. Инициация релиз-борда** — 1 дн.. Релиз-инженер НЕДРА загружает релиз (TOML, теги сервисов) в релиз-борд и запускает его. Далее шаги выполняются автоматически и в контуре ГПН; НЕДРА отвечает только за инициацию.

**19. Аудит кода** — 5 дн.. Первый шаг релиз-борда: аудит кода по зафиксированному тегу; проводит ИБ ГПН. Замечания возвращаются в устранение.

**20. Выкатка на UAT** — 1 дн.. Шаг релиз-борда: автоматическая выкатка релиза на UAT.

**21. Функциональное тестирование** — 1 дн.. Шаг релиз-борда: автоматическое функциональное тестирование выкаченного релиза.

**22. Решение «Нужен ли ПСИ ИБ» и ПСИ ИБ** — 0 дн. (не нужен) / до 5 дн.. Шаг релиз-борда: если ПСИ ИБ не нужен — шаг пропускается сразу; если нужен — релиз-инженер НЕДРА загружает документ, ИБ ГПН проводит ПСИ (до 5 дней).

**23. Согласование трансфера на ПРОД** — 5 дн.. Последний шаг релиз-борда: ИБ ГПН согласует перенос образов в Прод; проверяется, что digest образов совпадает с аудированным и указанным в TOML.

**24. Уведомление ГПН о начале работ на PreProd** — 1 дн.. Релиз-инженер НЕДРА уведомляет ГПН, что трансфер согласован и нужно начинать работы на PreProd. Дальнейшие шаги — в зоне ответственности ГПН.

**25. Выкатка на PreProd** — 1 дн.. DevOps ГПН выкатывает релиз на PreProd.

**26. БД PreProd: миграции** — 1 дн.. Администратор БД ГПН применяет скрипты миграции на PreProd.

**27. Брокеры PreProd: топики и настройки** — 1 дн.. Администратор брокеров ГПН применяет топики и настройки на PreProd.

**28. Регресс на PreProd** — 3 дн.. Тестировщик сервиса ГПН-ЦР проводит регресс на PreProd по тест-плану из ТестОпс ГПН-ЦР.

**29. Отчёт о регрессе PreProd** — 1 дн.. Тестировщик сервиса ГПН-ЦР фиксирует результат регресса и проверку отката. Совещания Go/No-Go нет: релиз идёт в Прод, если не сработал автоматический стоп-критерий (открытый Blocker без согласованного обхода). Правки — только на уровне helm, остальные критические дефекты — в hotfix.

**30. Организация уведомления пользователей** — 1 дн.. Release notes и changelog уже готовы (они нужны к TOML). Здесь только организуется рассылка: кому, когда, по какому каналу.

**31. Деплой в Прод** — 1 дн.. Релиз-инженер ГПН выкатывает релиз в Прод по TOML. Release owner НЕДРА инициирует выкат и получает подтверждение.

**32. Smoke PROD** — 1 дн.. Тестировщик сервиса ГПН-ЦР проверяет работоспособность в Проде; затем действует окно наблюдения (по мониторингу): при превышении порога ошибок — откат по плану из TOML.

**33. БД: пост-миграции** — 1 дн.. Администратор БД ГПН применяет пост-миграции в Проде.

**34. Брокеры: настройки в Проде** — 1 дн.. Администратор брокеров ГПН применяет настройки брокеров в Проде.

**35. Коммуникация ВНП с пользователями** — 2 дн.. После выката в Прод ВНП общается с пользователями: сообщает результат релиза, собирает обратную связь.

**36. Закрытие релиза и ретро** — 1 дн.. Release owner закрывает релиз и календарь; скрам-мастер проводит ретро (для hotfix, отката или инцидента — безвиновный постмортем в течение 5 рабочих дней); администратор проекта переносит ТРЗ задач этапов в ИСУП и 1С УПП.

## Критический путь

Самая длинная цепочка идёт последовательно: приоритеты бэклога → оценка и планирование спринта → сбор релизного тикета → подтверждение состава → спринт (разработка, скан в CI, тестирование, демо) → вывод не принятых задач → фича-фриз и тег → регресс на UAT → устранение багов и уязвимостей → Smoke UAT → инициация релиз-борда → аудит кода → выкатка на UAT → функциональное тестирование → ПСИ ИБ (если нужен) → согласование трансфера на ПРОД → уведомление ГПН → выкатка на PreProd, БД, брокеры → регресс на PreProd → отчёт PreProd → организация уведомления → деплой в Прод → Smoke PROD, БД и брокеры → коммуникация ВНП → закрытие и ретро. По принятым SLA это около 47 рабочих дней (9.4 недели) без ПСИ ИБ и около 52 рабочих дней (10.4 недели) с ПСИ ИБ; из них 10 рабочих дней — спринт. Параллельно идут разработка, скан в CI, тестирование и release notes внутри спринта; после фриза — регресс, финальный скан, подготовка TOML и импорт тест-плана; на PreProd — выкатка, БД и брокеры; после деплоя — Smoke PROD, БД и брокеры. Параллельные работы критический путь не удлиняют, пока укладываются в окна соседних этапов.

## Решения

| Шаг | Ответственный |
|---|---|
| Приоритеты бэклога на спринт | ВНП направления |
| Оценка задач и состав спринта (с учётом ёмкости QA) | РП направления с командой |
| Что должно войти в релиз (подтверждение состава) | ВНП направления |
| Приёмка задач на демо (демо проводит QA) | ВНП направления |
| Вывод не принятых задач из релиза и перенос в следующий релиз | РП направления по решению ВНП |
| Фича-фриз и тег релиза | Релиз-инженер НЕДРА |
| Готовность сборки после Smoke UAT (рекомендация) | QA |
| Инициация релиз-борда и уведомление ГПН о работах на PreProd | Релиз-инженер НЕДРА |
| Результат аудита кода, ПСИ ИБ (нужен или нет) и согласование трансфера на ПРОД | ИБ ГПН |
| Остановка релиза по стоп-критерию и снятие остановки (исключение) | Автоматически по критерию; исключение — ИБ ГПН (безопасность) или ВНП с тестировщиком ГПН-ЦР (функционал) |
| Эскалация просрочки этапа в контуре ГПН | Release owner (владелец процесса) |
| Откат релиза в Проде по плану из TOML | Релиз-инженер ГПН по критерию окна наблюдения |
| Результат регресса на PreProd | Тестировщик сервиса ГПН-ЦР |
| Выпуск в Прод (релиз идёт всегда; критические дефекты — в hotfix) | Release owner НЕДРА инициирует, релиз-инженер ГПН выполняет |
| Включение Bug в hotfix (внеплановая задача в спринт) | РП направления (Bug квалифицирует ВНП) |
| Деплой в Прод | Релиз-инженер ГПН |
| Перенос ТРЗ в ИСУП и 1С УПП | Администратор проекта |

## Метрики

| Метрика | Влияние | Формула | Ответственный |
|---|---|---|---|
| Время этапа | Показывает, где тратится время релиза | Готово − Старт задачи этапа | Ответственный за этап |
| Ожидание перед этапом | Показывает простои между этапами и на стороне ИБ | Старт этапа − Готово предыдущего этапа | Release owner |
| Длительность релиза | Соблюдение срока выпуска | Дата деплоя в Прод − дата старта приоритетов; сравнение с суммой SLA | Release owner |
| Соблюдение SLA этапа | Видно, какие этапы систематически выбиваются из SLA | Доля этапов, где время + ожидание ≤ SLA | Ответственный за этап |
