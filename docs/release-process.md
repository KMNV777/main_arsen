# Процесс ведения релиза ЕАРМ: регламент и реестр шагов

> Схема: [`drawio/10-release-process.drawio`](drawio/10-release-process.drawio) (5 страниц), превью — [`svg/10-release-process-1.svg`](svg/10-release-process-1.svg). Файлы генерирует `scripts/build_release_process.py` — правим данные в скрипте. Расхождения источников — [`release-process-review.md`](release-process-review.md).

Основа: «Эталонный процесс выпуска релиза» (Confluence NEDRA) и «Менеджмент команд разработки» (Jira). Нумерация шагов повторяет этапы эталона (колонка «Эт.»); новое отмечено ★.

## Цели

1. Показать **параллельные и последовательные** действия цикла: параллельный блок P (треки A — QA, B — уязвимости, C — ПСИ) со стыком на шлюзе G1.
2. Каждый шаг — задача Jira → время работы и ожидания по этапам собирается автоматически.
3. Чётко разделить **зоны ответственности** и закрепить ответственного за шагом (§14.1 эталона).
4. Видеть, **где, кем и на каком шаге** допущены ошибки, где ошибаемся в оценке и где нарушаются требования.
5. **Сервис** — часть процесса: в заголовке каждой страницы схемы, в поле задач и в матрице «сервис × этап».

## Последовательность и параллельность

1. **Ф0–Ф1 (последовательно):** 0.1 → 0.3 → 0.2 → 1.1 → 1.2 (Scope freeze) → 1.3 (freeze ветки, rc на UAT). ПМТ (3.1) стартует сразу, если ПСИ = Да.
2. **Ф2 — параллельный блок P** после rc: A = 4.1 → 4.2 → 4.3 ⇄ 4.4 (+ 4.5), B = 2.1 → 2.2 (gate ИБ), C = 3.1 → 3.2 → 3.3 (опц.). Стык — **G1 «Код-фриз»** (AND-join), фиксируется hash.
3. **Ф3 — цепочка ИБ-gates:** 5.1 → 5.2 (аудит) → 6.1 (ПТЗ) → 7.2 → 8.1 (трансфер). **TOML (7.1)** готовится параллельно аудиту и стыкуется на 7.2.
4. **Ф4:** 9.1 ‖ 9.2 → 10.1 → 10.2 → **G2 Go/No-Go** (No-Go → hotfix-цикл → 9.1).
5. **Ф5:** 11.1 → 12.1 → 12.2 ‖ 12.3 (БД и брокеры) → 12.4 (post-check) → 12.5 (merge в master) → 12.6 (закрытие, ретро).

## Ветки и отбор задач

Подробно — страница 2. Кратко:

- `master` = состояние Прода; `release/<сервис>/<версия>` режется от master в начале спринта.
- В ветку идут только Story/Bug из Fix Version с оценкой, тест-кейсами, кодовым инкрементом (PR → ключ Story) и скриптами миграции.
- Scope freeze (1.2) закрывает Fix Version; дальше — change control с кодом E1.
- Код-фриз (G1) фиксирует hash; аудит, ПТЗ, трансфер, PreProd и Прод работают с ним.
- 12.5: тег, merge release → master, перенос в открытые release/*.

## Jira и Confluence

- **Релизный Epic (квартал)** — как в эталоне; **Fix Version** — состав релиза; паспорт REL-XXX и календарь — витрина.
- **Задача шага** (Enabler/Task в Релизном Epic с fixVersion) на каждый шаг реестра; **под-задача сервиса** с полем «Сервис» — для шагов по сервисам.
- Старт = «В работе», финиш = «Готово»; возврат = новая задача того же шага + «Возврат из» + код E + этап внесения.

## SLA и критический путь

Норматив шага — от 1 до 5 рабочих дней (решение владельца процесса). Для каждого шага ИБ SLA = 5 дней (решение); остальные значения в реестре — **предложение**, нужно подтвердить; приём PR (1.1) идёт весь спринт и в SLA не входит. Расчёт — самая длинная цепочка от rc (1.3) до закрытия (12.6):

| Сценарий | Раб. дней | Недель | Путь |
|---|---|---|---|
| ПСИ + ПТЗ | 42 | 8.4 | 1.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 6.1 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6 |
| только ПСИ | 37 | 7.4 | 1.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6 |
| только ПТЗ | 42 | 8.4 | 1.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 6.1 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6 |
| без ПСИ и ПТЗ | 37 | 7.4 | 1.3 → 2.1 → 2.2 → G1 → 5.1 → 5.2 → 7.2 → 8.1 → 9.1 → 10.1 → 10.2 → G2 → 11.1 → 12.1 → 12.2 → 12.4 → 12.5 → 12.6 |

Превышение SLA шага (работа + ожидание) фиксируется метрикой M9 и кодом E6 (простой) или E7 (внешняя зависимость).

## Таксономия ошибок

| Код | Тип | Что фиксируем |
|---|---|---|
| E1 | Ошибка скоупа | Задача включена/исключена неверно; добавлена после freeze; расхождение Fix Version ↔ ветка |
| E2 | Ошибка оценки | Факт отличается от оценки более чем на порог (предлагается 25 %); недооценён регресс или фиксы |
| E3 | Нарушение регламента | Пропущен шаг, не выполнен критерий входа/выхода или правило §2; нет данных в Jira/паспорте |
| E4 | Дефект кода | Дефект внесён на этапе X, найден на этапе Y (фиксируем оба) |
| E5 | Окружение / сборка / доступ | Сбой стенда, CI, миграции, деплоя; нет доступа (подкоды из эталона §18) |
| E6 | Простой / ожидание | Ожидание ответа, ресурса или решения сверх норматива шага |
| E7 | Внешняя зависимость | Время и возвраты на стороне ИБ ГПН / ГПН-ЦР — фиксируем фактами |

## Решения владельца процесса

- Ветка режется от master (F1).
- ПТЗ — при необходимости: шаг 6.1 опциональный, флаг «Требуется ПТЗ» ставит релиз-инженер НЕДРА (F7).
- Hotfix идёт тем же процессом, что плановый релиз (F13).
- Юрченко Д. — релиз-инженер НЕДРА; БД — администратор БД Ибрагимов; брокеры — Степуляк (F11).
- Список сервисов пока не трогаем (плейсхолдеры в `SERVICES`).
- SLA шагов — от 1 до 5 рабочих дней; для каждого шага ИБ — 5 дней.
- Уязвимости, аудит и релиз-борд — зона ответственности релиз-инженера НЕДРА (Юрченко Д.).

## Нужно подтвердить

- Значения SLA неИБ-шагов (реестр) — предложены внутри диапазона 1–5 дней.
- Правка эталона и ДК: роль релиз-инженера НЕДРА, администраторы БД и брокеров, hotfix по полному процессу, ПТЗ по необходимости, правило переноса между релизами.
