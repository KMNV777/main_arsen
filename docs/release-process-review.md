# Ревью процессов выпуска релиза ЕАРМ

Сверены: (Э) «Эталонный процесс выпуска релиза» (Confluence NEDRA), (М) «Менеджмент команд разработки продуктовых решений», (С) прежняя схема процесса. Результат ревью положен в основу схемы — [`drawio/10-release-process.drawio`](drawio/10-release-process.drawio), регламент — [`release-process.md`](release-process.md).

## Что в процессах сделано хорошо

- Один набор правил для всех команд: единая таксономия Jira, Fix Version как единственный источник состава релиза, оценка у каждой задачи.
- Эталон описывает 13 этапов с владельцем, gate и критерием выхода; есть RACI, роли, доступы и привязка блокеров по доступам к этапам (§18).
- Обязательный объём релиза резервируется в ёмкости спринтов (Релизный Epic) — релиз не конкурирует с функционалом.
- Правила качества заданы явно: без тест-кейсов задача не попадает в релиз, миграции прикладываются, у Story есть кодовый инкремент.

## Итог для ведения релиза

1. Главные риски — не люди, а **отсутствие связки код ↔ этап** (F2) и **грубая единица учёта** (F3–F5): сейчас по Jira нельзя ответить, на каком этапе и в каком сервисе тратится время и допускаются ошибки.
2. Цепочка ИБ-gates идёт строго последовательно (аудит → ПТЗ → трансфер), но в таблице B эталона на неё отведено около недели из шести, а по SLA (ИБ — 5 дн на шаг) она занимает 12–17 рабочих дней (из них шаги самой ИБ — 10–15) (F17). Гипотеза «тормозит ИБ» проверяется метриками M2/M3/M9, а не оценками.
3. Пересечение циклов (F1, F10) — вероятный источник хронических проблем с ветками: правило переноса нужно утвердить в эталоне.
4. Решения, которые нужны от вас: список в конце [`release-process.md`](release-process.md).
