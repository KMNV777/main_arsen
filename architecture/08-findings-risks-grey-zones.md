# 08. Выводы, риски и «серые зоны» по каждой схеме

Документ структурирован по шести схемам ландшафта. Для каждой даются:

- **Выводы** — что архитектурно значимое следует из схемы (констатация фактов и их интерпретация).
- **Риски** — конкретные технические/операционные/комплаенс-риски с оценкой влияния и вероятности.
- **«Серые зоны»** — места, где исходный реестр (PDF) либо молчит, либо противоречит сам себе, либо использует размытые формулировки. Это то, что нельзя считать «известным» при принятии решений.

В конце документа — **сводный риск-реестр** и **карта серых зон** для быстрого использования в управленческих решениях.

> Шкала оценок:
> - **Влияние:** 🔴 Критическое / 🟠 Высокое / 🟡 Среднее / 🟢 Низкое
> - **Вероятность:** ▲▲▲ Высокая / ▲▲ Средняя / ▲ Низкая

## 8.1. Схема 01 — «Общий ИТ-ландшафт»

### 8.1.1. Выводы

1. **Ландшафт распадается на 4 типа систем по способу управления:**
   - Собственные разработки ДПППС/КМГИ (~14 систем) — ABAI, СДД, ИСОТ, Work, Procu/Price, АИСЭМ, Compliance Control, БДА, ЭА, Санау, УТО, АСДЦ, Бюро пропусков, корпоративные сайты.
   - Внешний вендор без альтернатив (~4 системы) — САПФИР (Directum), BoardMaps (Дэшборд Системс), Bitrix-порталы/сайты (1С-Битрикс24), SharePoint-системы (Microsoft).
   - Legacy под выводом (3 системы) — Электронный архив (Documentum), Санау, Бюро пропусков.
   - Унаследованная legacy без вендора (1 система) — АСДЦ (собственная разработка на устаревшем стеке).
2. **Active Directory — единая точка отказа всей экосистемы.** AD участвует в 12+ потоках интеграций, во всех SSO-сценариях, в синхронизации пользователей. Падение AD = остановка работы практически всех ИС.
3. **Внешние гос-зависимости концентрированы в трёх системах:** САПФИР↔ЕСЭДО, СДД↔НУЦ РК (TSP/OCSP), Compliance↔Kompra. Это даёт чёткие точки контроля комплаенса.
4. **«Самообслуживание» — иллюзия:** в схеме нет единой шины данных, нет API Gateway, нет общего IdP, нет общего ETL. Это означает, что **каждая интеграция — индивидуальный проект**, без типового шаблона.
5. **Сетка хостинга «двух VDC» создаёт латентность для критичных потоков:** SAP в Aqqol → АСДЦ в Aqqol (норм), но SAP в Aqqol → ABAI в Koshy (через сеть между VDC). Сетевые задержки в реестре не описаны.

## 8.2. Схема 02 — «Бизнес-домены и системы»

### 8.2.1. Выводы

1. **Сильное доменное «размывание» в документообороте:** четыре ИС с пересекающейся функциональностью — САПФИР (общий ДО), СДД (договоры), Электронный архив (хранение), BoardMaps (коллегиальные органы). Каждая со своим стеком, базой и владельцем — типичный случай «islands of automation».
2. **HR-домен фрагментирован:** Team (Bitrix24, kmg.kz), Work (work.kmg.kz), Bitrix ANPZ (anpz.kz), Bitrix Petrochem, Bitrix КМГ-Кумколь, плюс кадровые данные в 1С и SAP. Сотрудник ДЗО имеет 3+ точки входа.
3. **Технологическое разнообразие велико**, но просматриваются **два «стандарта де-факто»** для собственной разработки:
   - **Python-стек:** Vue + Django/DRF + PostgreSQL + Docker — ИСОТ, Work, Procu/Price, Compliance (с .NET), Электронный архив (FastAPI), ABAI.
   - **Microsoft-стек:** SharePoint + MS Project + MS SQL — Интранет, ИСУП.
4. **«Платформенные» ИС от Microsoft** (Интранет, ИСУП) и от Directum (САПФИР) — это закрытые экосистемы со своей моделью расширения; интеграция с ними возможна только через предусмотренные вендором API.
5. **Bitrix-кластер из 7 инсталляций** (4 портала + 3 сайта) — это либо результат децентрализованных закупок ДЗО, либо умышленное решение «по портал на дочернюю компанию». Архитектурно — отдельная зона ответственности.
6. **Логистика + HR + HSE на одной физической платформе** (УТО + Work + ИСОТ на srv1231602-08) — нетипичное архитектурное решение, экономия инфраструктуры в ущерб изоляции.

## 8.3. Схема 03 — «Потоки интеграций»

### 8.3.1. Выводы

1. **Архитектура интеграций — «спагетти» point-to-point.** 44+ потока без единой шины, единого API Gateway, единой стратегии повторов. Каждый поток — отдельная инженерная сборка.
2. **Цепочка SCADA-буферов dbLink — главный антипаттерн ландшафта.** 4 уровня MySQL-репликации между ДЗО и ABAI; время задержки ≤ 15 мин для **«ИС Upstream № 1 в КМГ»**. Это означает: ABAI не может быть честным real-time-инструментом для оперативного управления добычей.
3. **Несовместимость технологий интеграции внутри одной системы.** АСДЦ принимает данные в 4 разных форматах: SOAP/XML, TCP/IP byte, HTTP/XML, MS SQL Stored Procedures. Это означает, что любое масштабирование требует поддержки всех 4 стеков.
4. **Жёсткая зависимость СДД от НУЦ РК** (TSP+OCSP). Каждое подписание = онлайн-обращение к двум разным сервисам НУЦ. При недоступности — невозможно подписать документ.
5. **Двунаправленный обмен Team↔Work** существует, но **Work→Qsamruk помечен «в разработке»** — резюме внешних кандидатов пока не передаются в Фонд. Это означает, что HR-процесс не замкнут на отчётность Самрук-Казына.
6. **«Активный» AD-канал**: 12+ потоков аутентификации/синхронизации идут в реальном времени; синхронизация Compliance Control с AD раз в сутки — единственное исключение (по запросу).
7. **Полное отсутствие observability** интеграций: нет общего трейсинга, нет общих метрик, нет общих алертов. ELK есть только в САПФИР и СДД, Grafana+Prometheus — только в СДД. Падение потока обнаруживается «по жалобе пользователя».

## 8.4. Схема 04 — «Инфраструктура и хостинг»

### 8.4.1. Выводы

1. **QazCloud — стратегический поставщик инфраструктуры**, без которого ландшафт не существует. ~16 систем из 20+ размещены в QazCloud. Это означает критическую зависимость от одного провайдера IaaS.
2. **Распределение по двум VDC не основано на доменах безопасности** — это видно по составу: Koshy содержит ABAI (C/I/A 4/4/4) рядом с УТО (2/2/2); Aqqol содержит САПФИР (внешний документооборот) рядом с БДА (внутренние активы) и публичным сайтом КМГ.
3. **АСДЦ — «капсула времени 2014–2016 годов»:** ОС Win Server 2012 R2 (EOL октябрь 2023), MS SQL 2014 (EOL июль 2024), Ubuntu 14 (EOL апрель 2019). Это **2,5–7 лет без security-патчей** для системы C/I/A 3/3/3.
4. **CentOS 7 для ABAI (C/I/A 4/4/4)** — EOL 30.06.2024. Это **наивысшая категория информации на ОС без поддержки**. Без миграции после июля 2024 нельзя ставить даже коммерческие расширенные обновления RHEL ELS.
5. **GPU IBM POWER 9 + Tesla V100 на ppc64le** — крайне нетипичный выбор для ML 2025+ года. Большинство современных ML-фреймворков выпускают wheel-пакеты только для x86_64 и aarch64. Это создаёт «изоляцию» команды ABAI от остального сообщества Python ML.
6. **К Prod-серверам ИСУП и Интранета имеют технический доступ внешние администраторы** (ТОО «KMG DIGITAL», учётки Ushakov и Kenzhegaliev): учётки в AD отключены, но **остались в группе Remote Desktop Users**. Это **прямой security finding**.
7. **bastion-хостов нет.** Все админы работают с Prod напрямую через Checkpoint VPN. Нет central session recording, нет привилегированной сессии (PAM).
8. **5 единственных систем используют ELK / Grafana+Prometheus** (САПФИР, СДД, частично BoardMaps). 15+ систем — без централизованной observability.
9. **Бэкапы PostgreSQL ABAI хранятся на машинах в окружении Test/QA** — это не бэкап, это технически копия в той же сети. Нет 3-2-1 политики.
10. **GitLab двойной** (gitkmkl.kmg.kz + gitlab.contract.kmg.kz) — следствие изоляции команды СДД. Это означает несовместимость CI/CD, runner-ов, registry.

## 8.5. Схема 05 — «Данные и хранилища»

### 8.5.1. Выводы

1. **PostgreSQL — корпоративный стандарт ДПППС:** 9 систем используют PG как основной/единственный СУБД. Это упрощает миграции и DBA-компетенции.
2. **Разрыв версий PostgreSQL критичен:** 11 (БДА, Бюро) → 17 (Procu/Price). PG 11 ушёл из community support 14 ноября 2023. **Минимум 3 системы (БДА, Бюро, ЭА) — на неподдерживаемой версии**.
3. **MS SQL Server привязан к Microsoft-стеку** (SharePoint, MS Project, Directum) — это вынужденная зависимость, не выбор.
4. **MS SQL 2014 в АСДЦ** — основной массив аналитических данных компании на СУБД, выведенной Microsoft из mainstream support в июле 2019 года и из extended support в июле 2024 года.
5. **MySQL/MariaDB используется в двух разных контекстах:** Bitrix-инсталляции (массово) и SCADA-буферы ABAI (необычное применение). MySQL 5.7.36 на сайте КМКЛ — также за пределами поддержки Oracle (EOL октябрь 2023).
6. **Только одна система использует Vault** (BoardMaps), только одна — WAF (БДА). Это означает, что **секреты в большинстве систем хранятся в `.env` / `appsettings.json`** — критическое нарушение современных best practices.
7. **BigData-стек заперт в ABAI:** Druid, Spark, Kafka, Hadoop — никто кроме модулей ABAI не имеет к ним доступа. КМГ как организация не может проводить cross-system аналитику.
8. **Объектные хранилища фрагментированы:** MinIO (УТО, Procu), SeaweedFS (СДД), плюс файловые системы (САПФИР Directum, BoardMaps). Нет единого корпоративного S3.
9. **OLAP-DC АСДЦ на Win Server 2012 R2** — основной аналитический сервер компании на ОС, не получающей патчи 2+ года.
10. **C/I/A заполнен только у 5 из 20+ систем.** Реестр ОИБ не полон — это означает, что часть систем формально не классифицирована.
